# Hop3 0.7.0 Released

**Hop3 0.7.0** is out. It is the last release of the [NGI Zero](https://nlnet.nl/) grant that funded Hop3's Nix integration, and the headline redefines what "working" means.

## Twenty apps you can install, and a bar they have to clear

0.6 could browse the signed catalog. 0.7 installs from it (from the CLI or the dashboard) with an administrator account created for you at install time. Twenty applications ship in the official catalog: BookStack, Bugsink, Dolibarr, Easy!Appointments, Forgejo, Gitea, Invoice Ninja, Isso, Kanboard, Keycloak, LimeSurvey, Matomo, Mattermost, Miniflux, Nextcloud, Paheko, Radicale, Uptime Kuma, Vikunja and WordPress.

Each one ships a check that **signs in through the application's own authentication** with the credential Hop3 generated, reaches a page only a session can, and confirms a wrong password is refused. It runs at the end of every deploy (dashboard deploys included) and on demand with `hop3 app check --app <app>`. Publishing to the catalog requires one.

That sounds like plumbing, but it demanded twenty-three fixes across the platform.

## What happens when you stop accepting HTTP 200

Every application in the catalog deployed successfully and served a login page before this check existed. Bringing all twenty to a *real* login took twenty-three fixes, and almost all of them were in the platform rather than in the app recipes:

- apps were served over plain HTTP as well as HTTPS, so the `Secure` cookies most of them set were never sent back and every such login looped silently;
- PHP's built-in server ran with one worker, so any app that makes a request to itself during installation deadlocked against its own only worker; ten of the twenty run on that server;
- an install whose deploy failed could not be retried, because the app record was committed before the deploy was attempted;
- `[build].build` was read and then ignored by seven of the twelve language toolchains;
- `--clean` reclaimed Hop3's records of addon databases without reclaiming the databases, so the next install adopted a populated one.

None of those is visible to a deploy that returns 200.

## Then we pointed it at the Nix recipes

The catalog apps are packaged three ways (native, hand-written Nix, and Nix generated from a template) and only the native path had been checked this way. Applying the same bar to the other two gave 18 of 19 template-generated recipes and 16 of 16 hand-written ones.

Three days before that run, a deploy-oriented test matrix scored the hand-written Nix corpus **15 ok, 0 fail**. The sign-in check, on the same recipes, **failed all sixteen**; five of them turned out to be serving with no usable credential at all:

- **Radicale**'s authentication type came from a variable that defaulted to `none` and was never set. Every calendar and address book was public.
- **Isso**'s config had no administrator section, so its moderation dashboard was served disabled.
- **Miniflux**, **Keycloak** and **LimeSurvey** shipped literal passwords (`changeme`, `password123`) so the deployed instance had an administrator whose password is in our repository, while the operator held a generated one that did not work.

Every instrument we had reported those as working, because a server that authenticates nobody answers every request successfully. They are fixed, and each now refuses to start; the default fallback is gone. **If you deployed the Nix variants of those apps, redeploy.**

One more, found by reading recipes; no check would have caught it: both Nix packagings of **Gitea** and **Forgejo** deployed with open registration, because the setting that disables it lived in a shell script only the native recipe carried. An app with open registration signs in perfectly and refuses a wrong password: it passes the bar. The bar is a floor.

## The rest of 0.7

- **Safe upgrades.** `hop3 app upgrade` snapshots, redeploys, verifies, and restores the snapshot automatically if the build, a migration or the health check fails. `hop3 app rollback` restores on demand.
- **Email as a backing service** *(experimental)*. One transport configured once, inherited by apps that declare an email addon, with swappable backends: a provider relay, a dev sink that captures and never sends, or a self-hosted MTA that signs with DKIM and refuses to claim "ready" over unpublished DNS.
- **Content-aware health checks.** `[healthcheck].contains` means a deploy is healthy when the app serves its own page, not when it serves any page.
- **A published `hop3.toml` JSON Schema** and `hop3 scaffold`, so your editor validates the file as you type.
- **A web UI** covering the application lifecycle, addons, backups, environment and catalog install.
- **Firewall and WAF**: network-level rules plus an L7 WAF on the OWASP Core Rule Set.

The full list is in [CHANGES.md](https://github.com/abilian/hop3/blob/main/CHANGES.md).

## Takeaway

A deployment that builds, boots and returns 200 can still be an application nobody can log into; on one of our own corpora, that was true of sixteen out of sixteen while every test we had was green. If you operate a platform, the useful question is not whether your apps deploy. It is what your checks would still pass if the application were quietly broken.
