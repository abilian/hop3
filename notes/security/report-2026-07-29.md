Audited 255 files (1.9 MB, byte-ceiling truncated — `hop3-installer` and `hop3-testing` excluded by config and not in scope for the service threat model) against `notes/security/threat-model.md`. 8 candidate findings, **3 confirmed**, 4 refuted by verification, 1 needing input.

## Confirmed findings

### F1 — Critical: No rate limiting on RPC `auth get-token` — brute-force at wire speed

**File:** `packages/hop3-server/src/hop3/commands/auth.py:61`
**CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
**Status:** **NEW** — not reported in May or July 2026 rounds.

`AuthGetTokenCmd.requires_auth = False` allows unauthenticated calling via `POST /rpc`. The command performs bcrypt password verification at `auth.py:89` with **no per-IP rate limiting**. The web login path (`POST /auth/login`) applies `_AUTH_RATE_LIMITER.check()` at `server/controllers/auth.py:120` (5 attempts/minute/IP); the RPC path bypasses it entirely.

**What this means:** An unauthenticated attacker can attempt credentials at the speed of bcrypt hashing (~5-10/second on a modern CPU) instead of being throttled to 5/minute. That's roughly a 100x amplification. Combined with F2 (user enumeration), an attacker can first enumerate valid usernames, then brute-force their passwords.

**Fix:** Add rate limiting to the RPC path. Options:
- Reuse the existing `_AUTH_RATE_LIMITER` from `server/controllers/auth.py` by importing it in `rpc.py` and checking before dispatching `auth get-token`
- Create a separate rate limiter for the RPC auth surface
- Alternatively, move the rate-limit check into `AuthGetTokenCmd.call()` itself so any path to it is throttled

### F2 — High: User enumeration via distinct error messages in RPC `auth get-token`

**File:** `packages/hop3-server/src/hop3/commands/auth.py:81-90`
**CWE:** CWE-204 (Observable Response Discrepancy)
**Status:** **NEW** — not reported in May or July 2026 rounds.

`AuthGetTokenCmd.call()` returns three distinguishable outcomes:
1. Line 81-82: User not found → `"Invalid username or password"`
2. Line 85-86: User exists, inactive → `"Account is disabled"`
3. Line 89-90: User exists, wrong password → `"Invalid username or password"`

An attacker can detect disabled accounts (distinct message). Additionally, timing: `get_by_username` is ~milliseconds; `check_password` is bcrypt (~hundreds of ms). An attacker can differentiate "user exists, wrong password" from "user doesn't exist" by response time.

The web login path (`server/controllers/auth.py:143`) correctly collapses all failure modes into a single `"Invalid username or password"` message. The RPC path diverges.

**Fix:** Collapse the "Account is disabled" case into the same `"Invalid username or password"` message. For timing defense, run bcrypt on a synthetic hash when the user doesn't exist to normalize response time (with attention to not burning CPU on high-rate attacks — rate limiting from F1 would mitigate this).

### F4 — Medium: Admin-scoped JWT issued via un-rate-limited RPC path

**File:** `packages/hop3-server/src/hop3/commands/auth.py:99-103`
**CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
**Status:** **NEW** — related to F1, scored separately for the admin-scope blast radius.

The same un-rate-limited RPC path at `auth.py:99-103` appends the `admin` scope to the JWT when the authenticated user is an admin. The web login path constrains admin brute-force via rate limiting; the RPC path applies no such constraint, and no additional factor (such as forced 2FA, stricter rate limiting, or admin-notification on token issuance) is applied.

**Fix:** Same as F1 — add rate limiting to the RPC path. Additionally, consider a separate, stricter rate limit for accounts with `is_admin=True`, or notification on admin token issuance.

## Needs input

### F6 — Low: Magic link token consumed before user-existence validation

**File:** `packages/hop3-server/src/hop3/server/security/tokens.py:391`

`validate_magic_token` revokes the token at line 391 *before* checking that the user exists and is active at `auth.py:267-276`. If the user was deleted between generation and redemption, the token is burned without granting access. Low practical impact (5-minute TTL, no data loss, attacker burns their own token). The security-model.md §3.7 notes the fix path (make logout a POST), and this follows the same pattern of an operation that should be order-reversed. Needs a design decision: move the `get_by_username` + `active` check before `revoke_token`, or document as intentional (token already consumed = cannot be replayed, even if redemption fails).

All refutations accepted.

## Gaps in the threat model

1. **`auth get-token` via `POST /rpc` is not listed as a pre-auth entry point.** It is the primary CLI login path and the most security-critical pre-auth endpoint. The threat model should explicitly enumerate it alongside the web login surface.

2. **`GET /auth/login` (login page render) not listed.** Low impact (template rendering only, Jinja autoescapes), but the model should enumerate every unauthenticated route.

3. **SMTP plaintext password gap not carved into the credential-encryption invariant.** Security-model.md §3.4 documents the gap ("Encryption at rest is deferred platform-wide (M3.8)"), but this exception does not appear in the threat model's Invariant 7 or Out of scope sections. The model should note it.

4. **SSH git push → post-receive hook path.** The model lists the SSH entry point but does not document the internal trust chain: forced command → `extract_app_name_from_repo_path()` → app lookup by name. The name is derived from Hop3-controlled paths, but the trust assumption should be stated.
