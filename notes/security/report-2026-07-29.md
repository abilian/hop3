## Confirmed findings

### F1: Critical: No rate limiting on RPC `auth get-token`; brute-force at wire speed

**File:** `packages/hop3-server/src/hop3/commands/auth.py:61`
**CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
**Status:** **Fixed** (2026-08-01). Was NEW; not reported in May or July 2026 rounds.

`AuthGetTokenCmd.requires_auth = False` allows unauthenticated calls via `POST /rpc`. The command performs bcrypt password verification at `auth.py:89` with **no per-IP rate limiting**. The web login path (`POST /auth/login`) applies `_AUTH_RATE_LIMITER.check()` at `server/controllers/auth.py:120` (5 attempts/minute/IP); the RPC path bypasses it entirely.

**What this means:** An unauthenticated attacker can attempt credentials at the speed of bcrypt hashing (~5-10/second on a modern CPU), roughly a 100x amplification over the 5/minute throttle. Combined with F2 (user enumeration), an attacker can first enumerate valid usernames and then brute-force their passwords.

**Fixed.** The limiter instance and `client_ip()` moved from `server/controllers/auth.py` into `server/security/rate_limit.py` as `AUTH_RATE_LIMITER`, and the RPC dispatcher checks it before dispatch. Both transports now draw down one budget.

Of the three options the finding offered, the second (a separate limiter for the RPC surface) would have doubled the ceiling: two `RateLimiter(5, 60)` instances give an attacker 5 attempts per transport per minute, and the control remains per-transport. The instance being shared is the fix. The third option (check inside `AuthGetTokenCmd.call`) fails differently: the command has no access to the request, so it cannot key on client IP.

The dispatcher decides *which* commands to throttle from a declarative `Command.rate_limited` flag. A name check would miss an alias and the next pre-auth command someone writes. A test (`tests/a_unit/commands/test_rate_limited_commands.py`) fails when a `requires_auth = False` command appears that neither sets the flag nor is listed as verifying no credential; it caught one command (`help commands`) that this fix had otherwise overlooked. That test is the actual remediation; the limiter call is only the first thing it enforces.

The throttle honours `HOP3_UNSAFE`, mirroring the auth skip in `_check_authentication`; the flag cannot be set in production (`core/unsafe_gate.py` forces it off, §3.3.1), and test suites log in far faster than 5/min.

### F2: High: User enumeration via distinct error messages in RPC `auth get-token`

**File:** `packages/hop3-server/src/hop3/commands/auth.py:81-90`
**CWE:** CWE-204 (Observable Response Discrepancy)
**Status:** **Fixed** (2026-08-01). Was NEW; not reported in May or July 2026 rounds.

`AuthGetTokenCmd.call()` returns three distinguishable outcomes:
1. Line 81-82: User not found → `"Invalid username or password"`
2. Line 85-86: User exists, inactive → `"Account is disabled"`
3. Line 89-90: User exists, wrong password → `"Invalid username or password"`

An attacker can detect disabled accounts (distinct message), and timing leaks the same distinction: `get_by_username` is ~milliseconds, while `check_password` is bcrypt (~hundreds of ms). An attacker can differentiate "user exists, wrong password" from "user doesn't exist" by response time.

The web login path (`server/controllers/auth.py:143`) correctly collapses all failure modes into a single `"Invalid username or password"` message; the RPC path diverges.

**Fixed**, both halves. The three branches return one identical response object, and `orm/security.py::burn_password_check` verifies against a throwaway hash on the two branches with no real hash to check, so the timing matches too. The CPU concern the finding raises is answered by F1's limiter; the two fixes only work together, which §3.9 of the security model now states explicitly.

An existing test asserted the vulnerable behaviour (`test_auth_login_inactive_user` required the word "disabled" in the reply), so the fix had to invert it. A test can pin a defect in place; a green suite counts as evidence that a security property holds only when a test asserts that property. The replacement asserts all three failures are byte-identical.

### F4: Medium: Admin-scoped JWT issued via un-rate-limited RPC path

**File:** `packages/hop3-server/src/hop3/commands/auth.py:99-103`
**CWE:** CWE-307 (Improper Restriction of Excessive Authentication Attempts)
**Status:** **Fixed** (2026-08-01) by F1. Was NEW; related to F1, scored separately for the admin-scope blast radius.

The same un-rate-limited RPC path at `auth.py:99-103` appends the `admin` scope to the JWT when the authenticated user is an admin. The web login path constrains admin brute-force via rate limiting; the RPC path applies no such constraint, and no additional factor (forced 2FA, stricter rate limiting, admin-notification on token issuance) is applied.

**Fixed** by F1: the path is throttled, so the admin scope is no longer reachable by unmetered guessing.

The finding's two suggested extras were left out on purpose. A stricter limit keyed on `is_admin` cannot be applied before the password is verified without revealing which accounts are admins; it would reintroduce F2 in a new place. Notification on admin token issuance belongs with the control-plane audit log ([report-2026-07-21.md](report-2026-07-21.md), planned for 0.8), bolted onto no single command.

## Decided after the round

### F6: Low: Magic link token consumed before user-existence validation (resolved)

**File:** `packages/hop3-server/src/hop3/server/security/tokens.py:391`. Recorded before its resolution; see the **Resolved** note below.

`validate_magic_token` revokes the token at line 391 *before* checking that the user exists and is active at `auth.py:267-276`. If the user was deleted between generation and redemption, the token is burned without granting access. Low practical impact (5-minute TTL, no data loss, attacker burns their own token). Security-model.md §3.7 notes the fix path (make logout a POST), and this follows the same pattern of an operation that should be order-reversed. The design question: move the `get_by_username` + `active` check before `revoke_token`, or document the present behaviour as intentional (token already consumed = cannot be replayed, even if redemption fails).

**Resolved 2026-08-02 (0.7.1): the second answer.** Consumption-on-presentation stands as the behaviour; the ordering, and the rule that reconciles it with the plain-HTTP check going the other way, are recorded in security-model.md §3.7.2 and pinned by a unit test. The finding was real as a *documentation* defect: the code and the model disagreed, and the model was wrong.

## Refuted

4 findings refuted by clean-context verification. The refutations:

| ID | Finding | Refutation reason |
|----|---------|-------------------|
| F3 | No CSRF tokens on dashboard POSTs | The threat model's "Out of scope" table names this explicitly: CSRF tokens are excluded because every mutation is a POST + `samesite=lax`. An accepted risk. |
| F5 | Logout via GET enables CSRF forced-logout | Also in the threat model's "Out of scope": "`GET /auth/logout` is the known gap." Documented since May 2026. |
| F7 | sync_to_thread=False on blocking handlers | Blocks the event loop but is not a security defect; the authenticated user is operator-equivalent and only degrades their own dashboard. App serving is independent (uWSGI emperor, not ASGI). |
| F8 | Dead RPC git-hook path uses raw tar | The path reads `sys.stdin` (the server process's fd, `/dev/null` under systemd), which is not attacker-controllable through JSON-RPC. Returns before reaching `tar -xf`. The live path (SSH post-receive → `server/cli/git.py`) uses `extract_archive_to_dir`. |

All refutations accepted.

## Gaps in the threat model

### Gap 1: `auth get-token` via `POST /rpc` is not listed as a pre-auth entry point. **Closed**; the threat model's entry-point table now names it as its own row. Listing only `POST /rpc` in the table made the endpoint read as gated-by-auth when one command on it is pre-auth. The command, distinct from the transport, is the row that matters.

### Gap 2: `GET /auth/login` (login page render) not listed. **Already closed** at the time of writing: the entry-point table has the row.

### Gap 3: SMTP plaintext password gap not carved into the credential-encryption invariant. Security-model.md §3.4 documents the gap ("Encryption at rest is deferred platform-wide (M3.8)"), but this exception does not appear in the threat model's credential-encryption invariant or Out of scope sections. The model should note it.

### Gap 4: SSH git push → post-receive hook path. **Already closed** at the time of writing: the trust-boundary table carries the "SSH git push → app deploy" row with the forced command, the path-derived app name and `git archive` extraction.

Gaps 1 and 2 are closed; 3 stands open. Invariant 7 says credentials are encrypted at rest, while `plugins/email/email.py` holds `smtp_password` as a plain `str` and injects it into app environments as `SMTP_PASSWORD` / `EMAIL_HOST_PASSWORD` / `MAIL_PASSWORD`. The exception needs carving into the invariant; as written, the invariant is wrong.
