## Summary

The audit ran five times: once over the whole repository and once per package for `hop3-server`, `hop3-installer`, `hop3-cli`, and `hop3-rootd`. Triage kept a minority of the raw candidates — most of the rest were flows that cross no boundary in security-model.md §1.2, chiefly injection reported against the operator-local installer and CLI, where the "attacker" is the user typing the flag. The procedure changes that follow from that ratio are recorded in security-model.md §4.

The whole-repository run produced the material finding. The four package-scoped runs each concluded clean or near-clean while a systemic authorization gap sat between the RPC dispatcher and the command classes, visible only to a review that could see across both.

## 1. No per-resource authorization on app- and addon-scoped commands (High)

**Resolved as a model question; open as implementation work.** The audit surfaced this as an unqualified High. Triage established that the missing piece was a decision rather than a patch, and that decision has now been taken: **for 0.7 the control plane is single-tenant** — an authenticated account is an operator-equivalent credential, by design and stated as such. Per-resource ownership is planned work for a later release.

That reclassifies the finding without dismissing it. What remains is (a) the documentation duty, since an operator provisioning a second account must know it is not a confined one, and (b) the implementation, whose shape is set out at the end of this section.

Every RPC command authenticates the caller and none of the app- or addon-scoped ones authorize them for the resource they name. App and addon names are global identifiers with no owner:

- `orm/app.py` — `App` has no `owner`, `user_id`, or `created_by` column.
- `orm/addon_credential.py` — `AddonCredential` binds to an app, never to a user. An addon instance is a server-global object.
- `commands/_base.py` — `pass_username` defaults to `False`. Of **190 registered command classes, 18 set `pass_username = True` and 16 call `require_admin`** — all of them in `commands/user.py`, `commands/auth.py`, and the email plugin. Every app- and addon-scoped command is structurally unable to make an authorization decision, because it never receives the caller's identity.
- `server/controllers/rpc.py` — `_check_authentication` validates the JWT and stops. Scope membership is checked; resource ownership is not, because there is nothing to check against.

One valid low-privilege token therefore reaches `addon postgres query <any-name> --command "<any SQL>"`, the MySQL equivalent, `addon postgres restore` (destructive overwrite of another tenant's database), `addon attach --app` (copy any addon's credentials into an app you control), and the app lifecycle commands. The web dashboard has the same posture on its own surface: `dashboard/addons.py` lists every addon on the server for any authenticated session via `list_all_with_apps()`.

What made this worth escalating rather than filing as known behaviour: nothing had decided it. Hop3 ships multi-user auth, roles, an `admin` scope and magic-link login, and applies `require_admin` correctly across the user-management surface, so the resource layer looked like an omission rather than a choice. The documents disagreed too — an architecture overview aimed at MSPs promised "a multi-tenant, SaaS-compatible solution" while an encryption non-goal asserted single-tenancy in passing. The gap was in the deciding, not only in the code.

**Decision (0.7): single-tenant control plane.** Stated in `security-model.md` §1.4, reflected in [ADR 010](../adrs/010-security-and-resilience.md) (operational posture) and [ADR 011](../adrs/011-encryption.md) (one key per deployment, with the reasoning that per-account keys would protect nothing the authorization layer already grants). The technical report already argues the single-server case on these grounds, so the position is consistent across the deliverables.

**Done for 0.7 — documentation.** Operator-equivalence is now stated where an operator meets it: `hop3 user add` says so in its output (regression-tested), the admin guide's User Management section opens with it, and `docs/src/guides/security.md` leads with it. Leaving it in an engineering note only would have let the platform imply a separation it does not provide — the same class of problem as a silent failure.

**Planned — implementation.** When per-resource ownership lands:

- Add an owner to `App`, and an authorization step in the RPC dispatcher. The dispatcher is the seam that matters: 172 commands cannot each be relied on to remember.
- Invert the `pass_username` default so a command opts *out* of receiving the caller, making any future gap visible at review time rather than silent.
- Decide the migration for apps created before the column exists — every existing app needs an owner, and "assign them all to the first admin" is a decision with consequences, not a default.

Retrofitting ownership costs more the longer apps exist in the field, which is the argument for not letting this drift past its target release.

## 2. Installer input validation (High) — fixed

Three parameters of the CLI installer (`--branch`, `--version`, `--local-path`) and two of the deployer (`--host`, `--user`) were interpolated into command construction without validation, and the deployer's rsync invocation built its `-e` option string by concatenation. rsync hands `-e` to `popen("/bin/sh", "-c", …)`, so that one is a genuine shell context.

These sit on the operator's own machine, where the person supplying the value is the person running the command, so none of them is a privilege escalation. They are worth fixing regardless: the values also arrive from environment variables and from CI configuration, the deployer is the one installer component that talks to a remote host, and validation here costs a regex.

**Fixed** in `10998740`, roughly an hour after the run finished:

- `cli_installer/python.py` — `_GIT_REF_RE`, `_VERSION_RE`, `_validate_branch`, `_validate_version`, `_validate_local_path`, and `install_package` now builds `run_cmd([pip, "install", package_spec])` in list form.
- `deployer/config.py` — `__post_init__` calls `_validate_host` and `_validate_ssh_user`.
- `deployer/backends/ssh.py` — the `-e` option string goes through `shlex.join`, with a comment recording why rsync needs it.

## 3. `run_as_hop3` is a shell sink guarded by convention (Medium, structural)

`server_installer/user.py` — `run_as_hop3(cmd: str)` executes `["su", "-", HOP3_USER, "-c", cmd]`. Everything handed to it is parsed by a shell, and roughly fourteen call sites build that string with an f-string.

Every one of them is currently safe. User-derived package specs are `shlex.quote`d at the sink (`server_installer/python.py`), and the postgres password path is guarded by an explicit `_validate_postgres_password` shape check whose comment names the hazard: "An operator-customised password we can't safely interpolate into SQL". The codebase knows about this class and handles it site by site.

That is the concern. The safety is per-site discipline rather than a property of the seam, so it degrades silently the first time someone adds a call site without the quote — and the May rounds showed (security-model.md §2.2) that this is exactly how hardening drifts here.

**Fixed.** `run_as_hop3` now takes `list[str]` and joins with `shlex.join` at the seam; 16 of the 20 call sites moved to argv form. The remaining four genuinely need shell operators (`|`, `&&`, `2>/dev/null`) and use an explicit `run_as_hop3_shell`, whose docstring states that the caller owns quoting — shell use is now rare and greppable rather than the default.

Implementing it turned up a second hazard the audit had not named: `shlex.join` accepts a *string* and iterates it per character, so a future `run_as_hop3("pip install foo")` would have produced `p i p ' ' i n s t a l l ...` — a mangled command that still runs, under callers that mostly pass `check=False`. Silent corruption, not a type nit. The seam now rejects a string argument with an actionable `TypeError`.

## 4. Addon restore path reaches `psql -f` without containment (Medium)

`addon postgres restore <path>` passes an authenticated caller's path straight to `psql -f`, giving arbitrary file read as the `hop3` user — which includes other apps' addon-credential files. The Redis restore path has a weaker parallel.

This compounds with finding 1: the file read and the database overwritten are both freely chosen.

**Fixed.** `core/backup.py::resolve_backup_file` resolves the path and requires containment under the backup root, checking containment *before* existence so arbitrary paths cannot be probed. All three `restore()` implementations (Postgres, MySQL, Redis) call it. Sister-site sweep: `_clone` passes a platform-generated path and `import` reads stdin rather than a file, so neither needed it.

The containment root is passed in by the caller rather than read from config, which was not the first implementation. Rooting it at `HopConfig.BACKUP_ROOT` broke an integration test and exposed a real inconsistency — `backup()` writes under a module-level `HOP3_ROOT` that can diverge from the config instance. A validator that rejects the platform's own backups is worse than none, so writer and validator now share one root by construction.

## 5. Auth rate limiter is per-process (Low today)

`server/security/rate_limit.py` is an in-memory sliding window, and `server/controllers/auth.py` instantiates it at module level, so the limit is per worker process. The docstring already states the limitation.

There is no bypass today: the server runs Granian (`server/cli/serve.py`) and the systemd unit is a bare `hop3-server serve` with no worker count, i.e. one worker. The exposure appears the moment anyone scales it out, silently and with no error.

**Fixed.** `rate_limit.py` exports `LIMITER_STATE_IS_SHARED` (False), `serve.py` pins `WORKERS = 1` explicitly rather than by omission, and `check_worker_count` refuses the unsafe pairing at startup with a message naming the Redis-backed replacement. A latent config footgun becomes a fail-loud precondition.

Note what was *not* done: no `HOP3_WORKERS` setting was invented. Adding a knob in order to have something to assert on would create the very hazard the guard exists to catch. The invariant is pinned where the worker count is chosen, and a test asserts the shipped pairing is self-consistent — so raising `WORKERS` without moving the limiter to shared storage fails the suite.

The IP-keying half of this surface was fixed in an earlier round and re-verified clean: `auth.py::_client_ip` honours `X-Forwarded-For` only from a trusted peer and takes the rightmost entry.

## 6. `StrictHostKeyChecking=accept-new` in the deploy backend (Low)

`deployer/backends/ssh.py` accepts an unknown host key on first connection. That first connection is also the one that uploads and installs the platform as root, so a MitM positioned at exactly that moment succeeds silently.

Low severity for a developer tool against hosts the developer just provisioned.

**Documented, default unchanged.** The admin guide gains a "Verifying a host key before the first deploy" section with the `ssh-keyscan` / fingerprint-comparison procedure for hosts the operator did not provision. Changing the default to `yes` would break every legitimate first deploy to teach a lesson that applies to a minority of them; the operator who needs the guarantee can now get it.

## 7. Resource exhaustion (Low–Medium, robustness)

Three items from the whole-repository run, grouped because they will be met as reliability problems rather than as attacks:

- Streaming deploy spawns unbounded background build threads.
- `app create <repo_url>` runs `git clone` with no timeout, no depth limit, and no size cap.
- Redis db-number allocation has a race and a slot-exhaustion path.

These are the "apps must coexist without interference" rule going unenforced. Filed as robustness work.

## Confirmed clean

Re-verified during triage, worth recording because these are the surfaces most often re-flagged:

- **hop3-rootd** — no findings, and the run's 50-input × 22-op disposition table stands up to spot-checking. The binary allow-list of eight absolute paths, the single `exec.run` seam with `shell=False`, the `SO_PEERCRED` gate, per-op typed validators, and atomic state writes hold. The one substantive note (`APP_NAME_RE` duplicated between rootd and `hop3.core.identifiers`) is already covered by the cross-package parity test added in May.
- **hop3-cli** — no findings. The `ssh_target` leading-dash guard from the earlier round is intact and correctly applies its anchored allow-list to the whole target.
- **hop3-server injection surface** — SQLAlchemy parameterization throughout, Jinja2 autoescape plus `nh3.clean()` on catalog readmes, `find_icon()` containment with a raster-only extension allow-list, catalog signature verification, and the triple-gated `HOP3_UNSAFE` interlock all verified.
- **Dashboard mutations** — every state-changing dashboard route is a POST, consistent with the `samesite=lax` reasoning in security-model.md §3.7. The known `GET /auth/logout` gap is unchanged.

**On the third-party review.** We applied for the review offered alongside the grant and followed up twice with NLnet without hearing from an auditor. We would still welcome that review and will act on its findings whenever it arrives, but the milestone cannot stay open indefinitely waiting on a third party. So we audited the platform ourselves, with tooling we found and in part built — the `letscode` agent and its `vulnhunt` plugin — and processed the outcomes. That is what this report and its May counterpart record, and it is what we consider the milestone to rest on.

Worth being precise about what that substitutes for and what it doesn't. Automated analysis plus manual triage covers breadth well: it enumerated every input across every entry point, which is tedious and valuable. What an independent reviewer brings that we cannot supply for ourselves is a second opinion on the *enumeration* — an allow-list is only as good as the list, and the person who wrote it is the worst-placed person to find what is missing from it. That limitation is a reason to keep the offer open, not a reason to leave the milestone unfinished.

The audit also touches **M3.5** (firewall + WAF) and **M3.2** (upgrades) indirectly: `hop3-rootd`, which executes the privileged half of both, came through with no findings.
