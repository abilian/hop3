# Security review — May 2026 (0.5 release series)

**Rounds:** five, 2026-05-03 → 2026-05-08
**Scope:** whole repository, all packages
**Method:** LLM-driven review (Qwen) over the full codebase, one round per pre-release tag, with manual triage of every candidate before any fix
**Outcome:** 4 critical/high findings closed, ~30 further fixes, trust model written down

Published companion pages: [Security](../../docs/src/guides/security.md) for operators, [Security Model](../../docs/src/developers/security-model.md) for developers and auditors.

For the trust model, the audited-pattern catalogue, and the review procedure these rounds produced, see [security-model.md](security-model.md). This file records what the May rounds found and what was done about it.

> **Scope note.** Security review in Hop3 is continuous rather than periodic, and most of it never gets a write-up: findings are fixed in the ordinary course of work. Two rounds have been formalised — this one, and the earlier audit described in `docs/blog/posts/2026-05-security-audit.md` (published 2026-05-01, covering fixes that landed between October 2025 and April 2026: a command-injection sweep, per-IP rate limiting, a configurable token lifetime, RFC 7235 bearer matching). The rounds below are the ones that started 2026-05-03. Both are cited as M3.8 evidence; they are different rounds, so it is worth naming which is meant.

## Critical and high findings

### C-001 — Pre-auth admin takeover via magic link (critical)

`AuthMagicLinkCmd` was anonymously callable over RPC and defaulted `username="admin"`. Any HTTP client that could reach `/rpc` could mint a five-minute admin JWT — no credential required. This is a full pre-authentication compromise of the server.

**Fixed** in `0dbcbe2f`: `requires_auth=True`, the `username` default dropped, and a `require_admin` runtime guard added.

### H-001 — Magic-link scope accepted as a bearer token (high)

`VALID_SCOPES` included `magic_link`, so a token minted for magic-link redemption also satisfied the bearer-auth path and worked as a general five-minute token for any RPC command. The two credential types had been conflated.

**Fixed** in `0dbcbe2f`: `magic_link` dropped from `VALID_SCOPES`. Magic-link tokens are now validated only by the dedicated `validate_magic_token` at redemption, and are useless anywhere else.

### H-002 — Anonymous self-registration (high)

`AuthRegisterCmd` was anonymously callable, giving the RPC endpoint public self-registration on a platform that has no such feature by design.

**Fixed** in `0dbcbe2f`: `requires_auth=True` plus an admin gate. Provisioning goes through `hop3 user add`.

### H-004 — `DEBUG=True` hardcoded in production (high)

`server/asgi.py` hardcoded `DEBUG=True`, which forced `secure=False` on session cookies (sniffable over plaintext HTTP) and enabled Litestar debug-mode tracebacks in production responses.

**Fixed** in `0dbcbe2f`: driven by `HOP3_DEBUG`, defaulting to `False`.

### Addon SQL injection via unvalidated addon name (0.5dev1)

`db_name` flows into raw `CREATE DATABASE` / `GRANT` identifier interpolation, where the MySQL wire protocol offers no parameter binding. `AddonCreateCmd` did not validate `addon_name` before constructing the addon.

**Fixed** in `951c609d`: `validate_service_name` at the command, plus re-validation in `MySQLAddon.__post_init__` so a future code path that constructs the addon directly still fails closed. Documented as an audited pattern in security-model.md §3.1.1.

## Secrets handling

The recurring theme of rounds 2 and 4. The rule that came out of it — *credentials reach a subprocess via environment or stdin, never via argv* — is now security-model.md §3.4.

- **`mysqldump` / `mysql` client** used `-p{password}` on argv, exposing the addon password in `/proc/<pid>/cmdline` for the duration of every backup and restore. Switched to `MYSQL_PWD` (`c44d541d`). Postgres already used `PGPASSWORD` and audited clean.
- **Deployer admin-user creation** used `echo {pw} | sudo …`, leaking the admin password to any local user able to read `/proc`. Replaced with `subprocess.run(input=password)`, which required adding a `stdin` kwarg to the `DeployBackend.run()` contract and plumbing it through both the SSH and Docker backends (`c44d541d`).
- **Redis shipped unauthenticated.** The installer disabled `protected-mode` for Docker bridge access without setting a password, leaving the instance open to anything that could reach port 6379. Now generates a password, writes `requirepass`, and persists it to `/etc/hop3/redis-pass` (0640 `root:hop3`) for the server to read via `REDISCLI_AUTH` (`c44d541d`).
- **CLI auth-token file** was written non-atomically and world-readable. Now tempfile + `fsync` + `chmod 0600` + `os.replace` (`8b8b0db3`); the same fix was applied to `hop3-tui`, which shares the file, a round later (`9e506d49`).
- **`CommandError.__str__`** now redacts common password and token argv shapes, so a regression at a future call site cannot leak a secret through an error message. Defense in depth — keeping secrets off argv at the source remains the actual control (`8b8b0db3`).
- **Deployer password masking** showed the first and last four characters of the admin password, which leaks meaningful entropy for a generated secret. Dropped entirely (`c5a12518`).

## Injection and argument-injection guards

- **OS package lists.** `subprocess.run([pkg_manager, "install", "-y", *PACKAGES])` was safe only because every list is a static literal. Added `BaseOSStrategy._validate_package_names` at every `ensure_packages` override, rejecting shell metacharacters and a leading `-` — the latter caught by a test that showed `--reinstall` would otherwise have been injectable (`0d6e0c59`). Each list carries a "must remain static" comment.
- **PostgreSQL extensions.** App-declared extensions load as superuser, and several contrib extensions grant filesystem, network, or arbitrary-code capability to whoever can call them. Added an allow-list with a hard-deny set (`adminpack`, `dblink`, `file_fdw`, `postgres_fdw`, `pl{perl,python,tcl}u`) that the operator override cannot lift (`0d6e0c59`), later expanded with `HOP3_EXTRA_PG_EXTENSIONS` for popular self-hosted apps.
- **Proxy hostname interpolation.** `validate_hostname_list` guarded the nginx plugin from the start; Caddy and Traefik shipped a release without it, so an app deployer could inject proxy directives through newlines or `}` in `HOST_NAME`. Applied to both (`9e506d49`).
- **nginx `server_name` shape** validated (RFC 1035 plus the underscore wildcard) before any template interpolation in the installer (`c5a12518`).
- **CLI context names** validated at `context_add` and `context_rename` — rejects whitespace and metacharacters, caps length at 64 (`9e506d49`).

## Configuration and process interlocks

- **`HOP3_SKIP_CONFIG_VALIDATION`** was honoured unconditionally, letting anyone disable Pydantic validation of `hop3.toml`. Now ignored when `MODE=production`, mirroring the `HOP3_UNSAFE` gate; the escape hatch remains available in dev and test (`c44d541d`).
- **Developer-only Docker deploy backend** embeds a hardcoded test secret key. Added a top-of-file trust-model note and a runtime interlock refusing construction when `MODE=production`, so the test secret cannot reach a production deploy by accident (`0d6e0c59`).
- **Token revocation on DB error** now fails closed for admin-scope and magic-link tokens while keeping fail-open semantics for user scope, so a database outage does not lock every user out but also does not silently un-revoke an admin token (`9e506d49`).
- **hop3-testing** got an import-time `MODE=production` interlock, and an SSH-key tempfile race was closed with `mkstemp` + `fchmod` before write (`9e506d49`).

## TLS and certificates

- **CLI `_get_ssl_verification`** returned `False` — skipping chain validation entirely — for the IP-host-with-pinned-cert case, on the theory that an SSH-fetched certificate makes the hostname check redundant. It now returns the pinned cert path. Failing closed is correct (`c5a12518`).
- **Interactive "Disable SSL verification? [y/N]" prompt** removed from `hop3 login`. One wrong keystroke silently handed the auth token to an attacker-in-the-middle on every subsequent call. Replaced with a hard error listing three deliberate alternatives: SSH tunnel, pin a cert, or set `verify_ssl=false` persistently (`8b8b0db3`).
- **Self-signed certificate validity** dropped from 3650 to 365 days in the installer, matching the per-app cert path (`9e506d49`).
- **TUI** gained the `verify_ssl` and `ssl_cert` options threaded into its HTTP client, mirroring CLI policy (`9e506d49`).

## hop3-rootd

The privileged daemon was reviewed in its own round before merge, and again as part of each whole-repo round.

- `audit.sanitise_args` did not recurse into lists and tuples, so a list-of-dicts payload passed secrets through to the audit log unredacted (`c5a12518`).
- `_SECRET_FIELD_RE` was anchored with a trailing `$`, so it missed secret markers appearing mid-name (`aws_access_key_id`). Anchor dropped and the pattern set extended with `passphrase`, `passwd`, `private_key`, `signing_key`, `access_key`, `encryption_key`, `aws_`. The module's stated policy applies: false positives are acceptable, false negatives leak (`8b8b0db3`).
- `Server.bind()` now chowns the Unix socket to `root:hop3`; production via systemd already had `SocketGroup=hop3`, this closes the standalone path (`c5a12518`).
- `state.json` gets an explicit `chmod 0o600` after atomic rename, pinning permissions independently of the temp-file primitive (`c5a12518`).
- Audit log entries are `fsync`ed so a record survives a kernel crash in the page-cache window (`8b8b0db3`).
- A cross-package test now asserts that rootd's `APP_NAME_RE` matches `hop3-server`'s, so the duplicated regex cannot drift silently (`c5a12518`).

Remaining rootd work — systemd sandboxing and relocation out of `/home` — is deferred with rationale in [rootd-hardening.md](rootd-hardening.md) (still open as of 0.7).

## Known gaps left open

Recorded rather than fixed. Both are carried in security-model.md §3.7.

- **No CSRF middleware.** `samesite=lax` blocks the cookie on cross-site POSTs and every dangerous mutation is a POST, so the exposure is bounded. Two follow-ups remain: `GET /auth/logout` is a state-changing GET and therefore CSRF-able (forced logout, idempotent, no data loss), and the `Secure` cookie over plain `http://` causes a silent login loop that should fail loud instead.
- **One credential, two transports.** The web dashboard cookie and the CLI bearer token are the same JWT, so a leaked dashboard cookie is a full programmatic admin token. Minting web tokens with a distinct scope is the eventual fix.

## What the rounds taught us

Three lessons, all now folded into security-model.md §2.2 and §4:

1. **Sister-site bugs are the most reliable finding.** Every REAL item in the final round was a pattern already fixed elsewhere: `MYSQL_PWD` missed in the installer, `chmod 0600` missed in the TUI, `validate_hostname_list` missed in Caddy and Traefik. Fixing a hardening pattern is not done until the anti-pattern has been grepped for across all packages.
2. **Writing the trust model down paid for itself immediately.** In the first round after the document existed, the reviewing model began self-classifying findings as intentional-and-documented, and the recurring noise of earlier rounds largely stopped. Doc drift is a real bug.
3. **Rounds compound.** The whole-codebase round found C-001, which the preceding rootd-scoped review had no way to see; a later round caught certificate-validity drift that an earlier round had introduced into the doc. Cadence beats one-shot audits.
