## 1. hop3-rootd runs from a `hop3`-writable venv (HIGH: live escalation)

The only item here that is an exploitable path rather than hardening or debt.

rootd executes its interpreter and code from `/home/hop3/venv`, owned and writable by the unprivileged `hop3` user. A compromised `hop3` (which is to say code execution inside *any* deployed app, since all apps share that account) can overwrite rootd's code and trigger a restart, giving root with `CAP_NET_ADMIN`. [ADR 041](../adrs/041-privileged-operations-agent.md) §10 exists to eliminate exactly this, and its reference unit installs to a root-owned `/opt`.

Verified still true: `server_installer/rootd.py::_resolve_daemon_command` probes `VENV_DIR/bin/hop3-rootd` first; `/opt/hop3/.venv` is the third candidate and not where the installer puts it.

**Deferred by decision** (SF, 2026-08-01) as planned future work. Recorded here rather than only in [rootd-hardening.md](rootd-hardening.md) because that file reads as sandboxing debt, and this half is not: the sandbox is defence in depth, the relocation closes a privilege escalation. The same change unblocks both, which is the argument for doing them together.

## 2. Decisions outstanding

Neither is expensive to implement. Both are blocked on someone deciding, and both have now survived more than one round undecided, which is the reason to name them separately from the work.

### 2.1 Magic-link token is consumed before the user is validated (07-29 F6) — DECIDED

`validate_magic_token` (`server/security/tokens.py`) revokes the token before the caller checks that the user exists and is active. A user deleted between generation and redemption burns the link without getting in. Low impact: 5-minute TTL, no data loss, an attacker only burns their own token.

**Decided 2026-08-02 (SF): consumption-on-presentation is intentional; the code stands and the documentation was the thing that needed fixing.** The rule now written down in [security-model.md](security-model.md) §3.7.2 covers this case and the plain-HTTP one together — refuse before consuming when the holder can remove the obstacle within the token's life, consume when they cannot — so the two orderings stop looking like an inconsistency. A test pins it, because the ordering is invisible at the call site. Shipped in 0.7.1.

### 2.2 SMTP credentials contradict the credential-encryption invariant — DECIDED

**Decided 2026-08-11 (SF): invariant 8 was scoped to the database, and a defect the framing had hidden was fixed.**

The item as filed said email was the exception. It is not the exception; it is one of four. `save_addon_secrets` writes a **plaintext** JSON record for every provisioned addon, and PostgreSQL and MySQL put the database password in it (`postgres.py:467`, `mysql.py:232`) exactly as email puts the SMTP one. That file is also the *authoritative* copy — the Fernet `AddonCredential` row is the app-attachment derivative, read back from it. So the invariant was not missing a carve-out for one plugin; it was describing one of two stores and reading as though it described both.

Resolution, and why this way round: **encrypting the files would buy nothing.** `/etc/hop3/secret-key` is 0640 `root:hop3` and apps run as `hop3`, so any reader who can open the secrets files can also read `HOP3_SECRET_KEY` and decrypt the rows. The exposure is *`hop3` uid → every addon credential*, which is [ADR 055](../adrs/055-app-runtime-uid-separation.md)'s, already named under invariant 9, and encryption at this layer would look like a control while adding no boundary. Revisit after per-app UIDs land, when the reader and the key holder are no longer the same principal. Invariant 8 now states its scope; security-model.md §3.4.7 is the new entry, and §3.4.5 gained the pointer.

**What the framing was hiding.** Going to look at the store turned up a defect nobody had filed, in the writer all four addons share: it opened the file, dumped JSON, *then* chmod'ed 0600. Two consequences, both confirmed by running the old code — the password sat at 0644 (0666 under a permissive umask) for the length of every write and rotation, and because the open truncated the live file first, a failed write destroyed a working credential while the database went on expecting it. Fixed to `mkstemp` + `os.replace`, 0600 from birth, which is how `server/cli/setup.py` and the CLI's credential store have written credentials all along; this was the one site that had not caught up. Nine tests, including one that plants a 0644 file and one that fails the write mid-rotation.

Note the provider credential does *not* reach an app's environment under the relay backend (ADR 054 puts a loopback relay in between); this was about the server-level transport record.

**The lesson is §Coverage-gaps' one, from the other direction.** A doc inconsistency was filed as paperwork ("amend the invariant, ten minutes"), and the ten-minute amendment would have been written without opening `secrets.py`. The reason to go and look is that a claim which does not match the code is evidence about the code, not only about the claim.

## 3. Robustness items filed as security (07-21 finding 7)

Grouped in the July round because they will be met as reliability problems rather than attacks. All three are now fixed; sharpest first:

- ~~**`git clone` has no timeout, no depth limit and no size cap**~~ **Fixed 2026-08-09.** `clone_repository` in `core/git.py` runs the clone shallow and single-branch, under a wall-clock timeout and a byte cap, in its own process session so the transport helpers die with it, and removes the partial tree on any failure. Two things the finding did not say, both found on the way to fixing it: the line it cited (`core/git.py:158`) was in `GitManager.clone()`, which **had no callers** — the reachable clone was the one in `commands/app.py`, which is what the finding's own prose describes; and that call site passed the URL to git **unvalidated**, so `ext::sh -c …` (git runs it) and a leading `-` (git reads it as an option) both reached the command line. `validate_repo_url` now guards it, `--` separates it, and `GitManager.clone` is deleted. Recorded as [security-model.md](security-model.md) §3.1.5.
- ~~**Streaming deploy spawns unbounded background build threads.**~~ **Fixed 2026-08-09.** Every background build now goes through one bounded `BuildQueue` (`deployers/build_queue.py`): `MAX_CONCURRENT_BUILDS` run at a time (default 2), `MAX_WAITING_BUILDS` may wait (default 32), and past that a deploy is refused rather than queued. Both halves are loud — a refused deploy finishes its own stream with the reason, and a queued one says how many are ahead of it, because a build that has not started looks exactly like a build that has stalled. Recorded as [security-model.md](security-model.md) §3.3.4.
- ~~**Redis db-number allocation has a race and a slot-exhaustion path.**~~ **Fixed 2026-08-09.** The number is now chosen and written down in one critical section, under an exclusive `flock` on the addon-secrets directory (filesystem-level, because a CLI-side addon command and the server are separate processes). Before, allocation returned a number and the caller saved it only after pinging Redis, making it writable and setting a marker key — ten claims started at once got ten copies of db 1, which is ten apps sharing one database. Exhaustion: a create that fails after claiming releases the slot, and the refusal when all fifteen are taken names the addon holding each. This also corrected [security-model.md](security-model.md) §3.1.4, which claimed the collision was precluded when it was not.

These were the "apps must coexist without interference" rule going unenforced. Each is now enforced rather than assumed, and the Redis one is worth reading as a lesson about documentation: the model asserted the property, the code did not implement it, and nothing compared the two until someone went looking.

## 4. Scheduled platform work

Not defects; recorded so a review does not re-report them as findings.

- **Per-resource ownership**: `App.owner` plus an authorization step in the RPC dispatcher, with a migration decision for apps created before the column exists. The control plane is single-tenant *by decision* for 0.7 ([security-model.md](security-model.md) §1.4), and the documentation duty was discharged; the implementation is post-0.7. Retrofitting costs more the longer apps exist in the field.
- **Control-plane audit log**: rootd audits privileged operations; the RPC layer records nothing equivalent for logins, token issuance and revocation, or app and addon mutation. Targeted at 0.8 ([ADR 010](../adrs/010-security-and-resilience.md)).
- **Per-app UID separation**: [ADR 055](../adrs/055-app-runtime-uid-separation.md), Proposed. Until it ships, code execution in any app is equivalent to code execution as `hop3`. This is what makes item 1 reachable from a deployed app rather than only from a shell account.
- **CSRF tokens** for cookie-authenticated mutating routes. The `samesite=lax` + every-mutation-is-a-POST argument now holds without exception and is enforced by a test, so this is hardening rather than a gap.

## 5. Coverage gaps in the audits themselves

**The 2026-07-29 round hit its byte ceiling** — `hop3-installer`, `hop3-testing` and `hop3-tui` out of scope entirely, the email and Docker plugins partial, the Nix builder plugin possibly unreached. **Re-run on 2026-08-11 over exactly that scope** (~48k lines). What it found is below; what it did not find is worth as much, so both are recorded.

**No injection sink survived.** No `shell=True` outside one site (fixed, below), no `os.system`, no `eval`/`pickle`/`yaml.load`, no `verify=False` or unverified TLS context, no `extractall`, no `mktemp`. The sudoers fragment is four static literals and is being retired in favour of rootd. The Nix generator's escaping (`gen/escaping.py`) is the strongest code read in the round — it handles `${`, `''` and the lone-quote-adjacent-to-a-delimiter case, documents why each rule exists, and is doctested.

**The findings were all the same defect: something rendered or reported that was never measured.**

- **`hop3-tui` shipped a fabricated log viewer and a fabricated system dashboard.** `screens/logs.py` had no reference to the API client at all — it rendered eight hardcoded lines, including `[ERROR] Failed to connect to redis`, and appended an invented line roughly every three seconds so the pane looked live. `action_download_logs` would then write those invented lines to a file in `~/Downloads` for an operator to attach to a bug report. `screens/system.py` reported CPU 42% / memory 63% / disk 81% as constants on a five-second timer, an info panel claiming `hop3.dev` running `v0.5.0` with 14 days of uptime, and a services panel that *discarded the status dict handed to it* and rendered nginx/supervisor/postgresql/redis as RUNNING unconditionally. **`Hop3Client.get_app_logs` already existed and was simply never called**, so the log pane is now wired to it and every failure mode names itself on screen; the system panels render "not reported by the server" until `get_system_status` parses its response (its own docstring already tracks that). Ten tests, each asserting the absence of the specific fabrication as well as the presence of the real value.
- **`hop3-testing`'s `add_host_key` built a shell command string.** `ssh-keyscan -p {port} … {host} >> {known_hosts} 2>/dev/null` with `shell=True`: the host was operator-supplied so this was not a live injection path (the threat model puts workstation self-injection out of scope), but a host containing a space ran something other than the intended command, and `2>/dev/null` meant a failing scan returned `False` with no reason anywhere. Now an argv list with the failure reported; five tests.

**Two deferrals, recorded so the next round does not re-report them.** The Nix installer (`server_installer/nix.py`) and `get-pip.py` (`cli_installer/python.py`) are downloaded over verified HTTPS and executed with no checksum or signature check; upstream compromise is the residual risk and pinning a hash is the fix, when someone owns the bump procedure that comes with it. The `urlretrieve` for `get-pip.py` also has no timeout, unlike its sibling.

**Where the TUI's *other* mock paths stand.** Every screen has a `if not self.hop3_app:` fallback rendering sample data (backups, addons, env vars, apps, processes, system logs), and the mutating ones notify "API not available — destroy simulated" rather than claiming success. `hop3_app` is `hasattr(self.app, "api_client")`, and `Hop3TUI.__init__` always constructs one, so these are unreachable in the shipped binary and truthful if reached. Left alone deliberately: they are test scaffolding wearing a production-looking guard, and rewriting them is a refactor, not a fix. The two that *were* fixed had no such guard.

**Package-scoped rounds are structurally blind to the findings that matter most.** The 2026-07-21 round ran four package-scoped audits that each concluded clean while a systemic authorization gap sat between the RPC dispatcher and the command classes. Already recorded as procedure in [security-model.md](security-model.md) §4.2; repeated here because the scope decision gets made again every round.

**No third-party review has happened.** Applied for alongside the grant, two follow-ups to NLnet, no contact from an auditor. An independent reviewer supplies a second opinion on the *enumeration* that we cannot supply for ourselves. An allow-list is only as good as its list, and its author is the worst-placed person to find what is missing from it. Keep the offer open.

## What the last two rounds have in common

The most transferable thing on this page. Of the five items closed on 2026-08-01, four were rules the codebase applied nearly everywhere. Each had one site out of step and nothing checking: the limiter applied to one of two login transports, the uniform error message applied on one of two paths, the POST-only rule holding for every mutation but one, the no-argv rule holding at every sink but documented only in comments.

Every one of them had been thought about. The thinking lived in prose (a `# SECURITY:` comment, a doc section, a convention) where nothing re-checked it as the code moved. The fix that generalises is the tests. Each now has a test that fails when the next site drifts, and the guard test for rate limiting found a command (`help commands`) the manual fix had missed on its first run.

So: when a round closes a finding, ask what makes the *class* fail loudly next time, and prefer that over the patch. §4.5 of the security model says sweep sister sites; this adds that a sweep is a point-in-time act and a test is not.
