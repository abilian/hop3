## Executive Summary

Hop3 is an open-source Platform as a Service (PaaS) that enables deployment and management of web applications on single servers. Designed for digital sovereignty and simplicity, Hop3 provides a self-hostable alternative to multi-node container-orchestration systems, targeting small-to-medium businesses, managed service providers, non-profits, educational institutions and developers who need to run multiple web applications on a single server without adopting a full container-orchestration stack.

This interim technical report documents the architecture, implementation status and security features of Hop3 as of April 2026. It supersedes the February 2026 draft (v1.0) and reflects progress made during Q1–early-Q2 2026, in particular the completion of the two largest NGI deliverable strands (Nix integration, T1–T2; packaged applications, T4) that were at 0 % in the prior report.

**Key Achievements (as of April 2026):**

- Client-server architecture with JSON-RPC communication over SSH tunnels or HTTP/HTTPS.
- Plugin-based extensibility: seven plugin types (builders, language toolchains, deployers, addons, proxies, OS implementations, health checks) with a total of ~25 concrete implementations.
- Support for 9 programming languages across 33 deployment tutorials.
- **Nix integration delivered** (T1 + T2): hand-crafted `hop3.nix` expressions and an eight-template auto-generation system; 43 Nix application packages validated end-to-end.
- **99 real-app variants packaged** (T4): 29 Docker, 27 native, 23 hand-crafted Nix, 20 template-generated Nix — covering PHP, Node, Go, Python, Java, Ruby and Rust ecosystems.
- **S3-compatible object storage addon** shipped (backend-swappable abstraction; MinIO in 0.5, Garage planned for a later release).
- **Structured diagnostics** (`Diagnosis` dataclass) across the deployment pipeline, producing actionable error messages of the form *[Component] can't [action]: [reason]. [Hint].*
- Security hardening: JWT bearer-token case-insensitivity (RFC 7235), in-memory rate limiter on authentication endpoints, magic-link default-username removed, session lifetime configurable via environment variable.
- 943 automated tests passing (up from 638 in v1.0), with per-test runtime-log collection on failure so a single test-suite run is self-sufficient for debugging.

## 1. Introduction

### 1.1 Project Background

Hop3 addresses the gap between heavyweight container orchestrators (Kubernetes and derivatives) and ad-hoc provisioning scripts. Container orchestration is a strong fit for multi-node high-availability deployments but imposes operational overhead (distributed consensus, kubelets, service meshes) that is disproportionate to the common case of deploying a handful of web applications on a single server. Hop3 targets that case:

- **Simplicity.** Application deployment follows familiar PaaS conventions (git push, CLI commands); the operator does not write YAML manifests.
- **Sovereignty.** The stack is self-hosted end-to-end; no external control plane or licence server is required.
- **Security.** Authentication is required on every RPC; credentials for addons are encrypted at rest (see §5).
- **Small footprint.** The control plane runs as a single Python process; a formal resource-footprint measurement is planned for the 0.6 release (see §10).

### 1.2 Target Users

Hop3 serves multiple user communities:

| User Type | Primary Needs |
|-----------|---------------|
| **SMB IT Administrators** | Centralized management, easy migrations, reliable backups |
| **Managed Service Providers** | Multi-tenant deployments, scalable client management |
| **Developers/DevOps** | CI/CD integration, consistent environments, rapid iteration |
| **Educational Institutions** | Manageable infrastructure, secure data handling |
| **Non-profits** | Cost-effective solutions, minimal technical expertise required |

### 1.3 Design Principles

1. **Convention over configuration.** An application with a `Procfile` and no `hop3.toml` deploys with defaults; `hop3.toml` is only required when the operator needs non-default behaviour.
2. **12-Factor App compliance [6].** Environment-based configuration, stateless processes, process-based scaling.
3. **Plugin-first architecture.** Seven plugin categories (builders, language toolchains, deployers, addons, proxies, OS implementations, health checks) cover every extension point; core code does not special-case individual implementations.
4. **Fail-fast, structured errors.** Failures surface through a structured `Diagnosis` carrying a component, action, reason and hint (see §5); a terse `raise Abort("deploy failed")` is considered a regression.
5. **Authentication on every request.** The JSON-RPC surface refuses unauthenticated calls; addon credentials are encrypted at rest.

### 2.2 Communication Flow

1. **CLI/TUI** parses user commands and validates input
2. **SSH Tunnel** established for secure communication (or direct HTTPS)
3. **JSON-RPC** request sent to server endpoint
4. **Server** authenticates request via JWT token
5. **Command Handler** processes request through appropriate plugins
6. **Response** returned to client with structured output

## 3. Package Structure

Hop3 is organized as a monorepo with five main packages:

### 3.1 hop3-server

The core server component that runs on deployment targets.

| Component | Technology | Purpose |
|-----------|------------|---------|
| Web Framework | Litestar (ASGI) | HTTP API and web UI |
| Database | SQLAlchemy + Advanced Alchemy | ORM and migrations |
| Plugin System | Pluggy | Extensibility framework |
| Dependency Injection | Dishka | Service container |
| Process Manager | uWSGI | Application runtime |

**Key Responsibilities:**
- JSON-RPC API for CLI/TUI communication
- Application deployment orchestration
- Reverse proxy configuration
- Database addon management
- User authentication and authorization

### 3.2 hop3-cli

Thin client for remote server management.

**Features:**
- JSON-RPC over SSH tunneling
- Rich terminal output with color formatting
- Confirmation prompts for destructive operations
- Local configuration management

### 3.3 hop3-installer

Installation and deployment toolkit.

| Command | Purpose | User |
|---------|---------|------|
| `hop3-install cli` | Install CLI on local machine | End users |
| `hop3-install server` | Install server on target machine | Sysadmins |
| `hop3-deploy` | Deploy/update during development | Developers |

**Design Constraint:** No runtime dependencies (stdlib only) to ensure reliable bootstrap.

### 3.4 hop3-tui

Terminal user interface built with Textual.

**Features:**
- Real-time dashboard with system metrics
- Application management interface
- Live log streaming
- Environment variable editing

### 3.5 hop3-testing

Test framework and fixtures for E2E testing.

**Capabilities:**
- Unified test runner (`hop3-test` CLI)
- Docker-based test infrastructure
- Test catalog with `test.toml` support
- Multiple target types (Docker, SSH, ready images)


## 4. Plugin System

Hop3 uses [Pluggy](https://pluggy.readthedocs.io/) for its plugin architecture, enabling extensibility without core modifications.

### 4.1 Plugin Types

| Type | Purpose | Examples |
|------|---------|----------|
| **Builders** | Orchestrate build process | LocalBuilder, DockerBuilder |
| **Language Toolchains** | Language-specific build logic | Python, Node, Ruby, Go, Rust, Java, PHP |
| **Deployers** | Run built artifacts | uWSGI, Docker Compose, Static |
| **Addons** | Backing services | PostgreSQL, MySQL, Redis |
| **Proxies** | Reverse proxy configuration | Nginx, Caddy, Traefik |
| **OS Implementations** | Operating system abstraction | Debian family, Red Hat family |
| **Health Checks** | Service health monitoring | Database connectivity checks |

### 4.2 Hook Specifications

Plugins implement hooks defined in `hop3/core/hookspecs.py`:

```python
@hookspec
def get_builders() -> list[type[Builder]]:
    """Return builder implementations."""


@hookspec
def get_language_toolchains() -> list[type[LanguageToolchain]]:
    """Return language toolchain implementations."""


@hookspec
def get_addons() -> list[type[Addon]]:
    """Return addon implementations."""


@hookspec
def get_health_checks() -> list[HealthCheck]:
    """Return health check implementations."""
```

### 4.3 Example: Health Check Plugin

```python
class PostgresHealthCheck:
    name = "postgresql"

    def is_configured(self) -> bool:
        return PostgresAdmin.from_config().password is not None

    def check(self) -> HealthCheckResult:
        try:
            # Verify PostgreSQL connectivity
            admin = PostgresAdmin.from_config()
            admin.test_connection()
            return HealthCheckResult(
                name="PostgreSQL", passed=True, message="Connection successful"
            )
        except Exception as e:
            return HealthCheckResult(name="PostgreSQL", passed=False, message=str(e))


class PostgresPlugin:
    @hookimpl
    def get_health_checks(self) -> list:
        return [PostgresHealthCheck()]
```


## 5. Security Features

### 5.1 Authentication

**JWT Token Authentication:**
- Tokens issued upon successful login
- Configurable expiration (default: 24 hours)
- Token revocation support for logout
- Bcrypt password hashing (cost factor 12)

**Role-Based Access Control:**
- Admin and user roles
- Permission checks on sensitive operations
- Audit logging for security events

### 5.2 Credential Management

**Fernet AEAD Encryption:**
- Service credentials encrypted at rest
- Key derivation via PBKDF2-HMAC-SHA256
- Requires `HOP3_SECRET_KEY` environment variable

```python
# Credential encryption flow
key = derive_key(HOP3_SECRET_KEY, salt)
fernet = Fernet(key)
encrypted = fernet.encrypt(credential.encode())
```

### 5.3 Secure Communication

- SSH tunnel support for CLI-server communication
- HTTPS support with automatic certificate management
- Input validation on all API endpoints
- SQL injection prevention via parameterized queries

### 5.4 Security Audit Outcomes

The following issues were identified in internal review during Q1 2026 and fixed as part of milestone M3.8 (code portion). An external review is pending and scheduled for release 0.6.

| Issue | Status | Mitigation |
|-------|--------|------------|
| JWT Token Tampering | Fixed | Signature verification enforced |
| SQL Injection | Fixed | Parameterized queries throughout |
| Hardcoded Passwords | Fixed | Removed; environment-based configuration |
| Authentication Bypass | Fixed | Middleware validates all non-public routes |
| Credential Exposure | Fixed | Encrypted storage with Fernet (AEAD) |
| Magic-link default username | Fixed | `default="admin"` removed from the CLI |
| Bearer token case sensitivity | Fixed | Case-insensitive match per RFC 7235 |
| Session lifetime not configurable | Fixed | `HOP3_TOKEN_EXPIRY_HOURS` env var |
| No rate limit on auth endpoints | Fixed | In-memory sliding-window limiter (5 req/min/IP) on `/auth/login` and `/auth/magic/{token}` |

**External review:** Not yet performed. The internal audit list above and the corresponding regression tests will be shared with a third party for validation before the final report.

### 6.2 Diagnostic Infrastructure

Because the 99-app end-to-end suite reveals failures that are inherently distributed (an app may fail in its container, in uWSGI, in the reverse proxy, or in an addon), the test framework now collects per-test runtime logs *before* the runner's cleanup step destroys the container. Each failing test produces a self-contained log file with:

- App directory layout on the target
- uWSGI worker log tails (last 80 lines per worker)
- Application build log
- Generated nginx configuration
- Generated uWSGI configuration
- Docker container state and `docker logs` output for every matching container

This eliminates the need for an operator to SSH into the target and reconstruct the failure manually, reducing mean-time-to-diagnosis from minutes to seconds.

## 10. Future Work

The 0.6 release (final NGI deliverable) is scheduled for mid-to-late
2026. The scope that remains is narrower than in the v1.0 draft because Nix integration (T1, T2) and application packaging (T4) are largely delivered. Remaining work clusters around three strands:

### 10.1 Multi-service applications (ADR 038)

The current `[run.workers]` model handles same-process-tree workers (web + cron + queue sharing env vars and addons). Architecturally more complex apps — Mastodon (Rails web + Sidekiq + Node streaming), AppFlowy (PostgreSQL + Redis + MinIO + GoTrue + workers), NextCloud (web + cron) — need per-component resource limits, per-component health checks, and independent scaling. ADR 038 specifies the `[[component]]` schema; Phase 1 (schema + parser) is scheduled for 0.6, Phase 2 (runtime support) for 0.7.

### 10.2 Quantitative evaluation

The evaluation section of the final paper and the final technical report requires measurements that have not yet been collected:

- Control plane memory footprint compared to K3s, Docker Compose and bare uWSGI under equivalent workloads.
- Deployment time from `git push` to running application, across the four build strategies (Docker, native uWSGI, hand-crafted Nix, template-generated Nix).
- Nix closure sizes compared to equivalent Docker image sizes, including the delta-transfer bandwidth savings when upgrading an application.
- Application cold-start latency under uWSGI emperor mode.

These measurements will be collected on the 99-app variant corpus using a dedicated benchmark harness, and reported in the final paper submitted for peer review.

### 10.3 Operational hardening

- **Firewall/WAF integration (M3.5):** design complete, implementation in 0.6.
- **External security audit (M3.8):** scheduled for 0.6; internal audit outcomes listed in §5.4 will be shared with a third party for validation.
- **Web UI (M3.7):** basic dashboard is functional; app editing, addon management and live log streaming are scheduled for 0.6.
- **Screencasts (M5.6):** user-facing video documentation, 0.6.
- **Production deployments (M4):** five applications running in sustained production with periodic experience reports (first drafts of 20 such reports already written; production validation still pending).


## 11. Conclusion

Between the February 2026 interim report (v1.0) and this April refresh, the project has converted two of its largest NGI deliverable strands from "not started" to "delivered": Nix integration (T1, T2) and application packaging (T4). A production-grade diagnostic-log pipeline and an S3-compatible object-storage addon were also added; both were needed to support the packaged-applications goal and are reusable by future addons.

Quantitatively:

- 9 programming languages supported via native toolchains.
- 99 application-variant deployments validated end-to-end on a remote VPS, covering 20+ distinct open-source applications across four build strategies (Docker, native, hand-crafted Nix, template-generated Nix).
- 943 unit + integration tests passing.
- Structured `Diagnosis` error messages replace bare tracebacks at every major failure point in the deployment pipeline.
- Per-test runtime-log collection produces self-contained failure reports without requiring manual inspection of the target server.

The remaining work for the final NGI deliverable (release 0.6) focuses on quantitative evaluation against existing orchestrators, multi-service application support (per ADR 038), external security audit, and the final peer-reviewed publication.
