## Abstract

We present **Hop3**, an open-source Platform-as-a-Service (PaaS) designed for deploying and managing web applications on a single server. Hop3 occupies a position between two dominant points on the deployment spectrum: heavyweight container orchestrators (Kubernetes and derivatives), which impose multi-node infrastructure and significant operational overhead, and ad-hoc provisioning scripts, which lack reproducibility and lifecycle support. The system provides a git-push-based deployment flow and a CLI/TUI interface backed by a JSON-RPC server; internally, a plugin architecture separates builders, language toolchains, deployers, addons, and reverse proxies. A central contribution of this report is Hop3's **Nix-based reproducible build path**, an alternative to Docker-first deployment that exercises three tiers of reproducibility (nixpkgs-source, `__noChroot`, and prebuilt-artifact) through eight code-generation templates. We describe the architecture, the plugin model, the Nix integration, the backing-service abstractions (PostgreSQL, MySQL, Redis, S3-compatible object storage), and the diagnostic infrastructure that captures distributed failure context before cleanup. We report preliminary qualitative evaluation covering 99 end-to-end application-variant deployments across 20+ real open-source applications and four build strategies. Quantitative benchmarking against K3s, Docker Compose and bare uWSGI is deferred to the final report.

**Keywords:** Platform-as-a-Service, single-server deployment, Nix, reproducible builds, digital sovereignty, self-hosting, deployment automation, plugin architecture.

## 1. Introduction

### 1.1 Motivation

Deploying a web application onto a server today typically requires a choice between two unsatisfactory options. On one end, container orchestrators such as Kubernetes [1] and its single-node derivatives (K3s, Minikube) provide reproducible, declarative deployments but at the cost of multi-component control planes (etcd, kubelet, scheduler, controller manager), YAML manifests, and operational complexity that is disproportionate to the common case of running a small number of web applications on one host. On the other end, ad-hoc provisioning scripts and hand-written `systemd` units offer simplicity but no reproducibility, no lifecycle support, and no abstraction over backing services.

A large class of real operators — small and medium businesses, managed service providers, non-profits, educational institutions, and independent developers — sits between these two extremes. For this class, the dominant deployment pattern is still a single machine (or a small number of machines) running multiple applications side by side, often with a reverse proxy in front and one or more shared database instances behind. The operator wants automated deployment, basic lifecycle management, and reproducibility, without paying the cost of a distributed control plane.

Hop3 targets this gap. It provides a PaaS with a git-push deployment flow comparable to Heroku and Dokku [2,3], a plugin-based extensibility model, authentication on every control-plane request, and — as the principal technical contribution of the current project phase — a Nix-based alternative build path that offers a credible reproducible-build story without requiring a container runtime at all.

### 1.2 Contributions

This report documents the state of the Hop3 project as of April 2026 and describes the following concrete artefacts:

1. **A plugin-based PaaS architecture** with seven plugin categories (builders, language toolchains, deployers, addons, proxies, operating-system implementations, health checks) covering the full deployment pipeline. The architecture is implemented in Python on top of Litestar (ASGI), Pluggy, SQLAlchemy, and Dishka dependency injection.
2. **A Nix integration subsystem** consisting of (a) a hand-crafted `hop3.nix` build path, (b) an eight-template auto-generation system covering the recurring packaging patterns observed across the application catalogue (see Appendix B), and (c) a runtime contract (`$out/hop3/runtime.json`) that decouples the Nix derivation from the Hop3 runtime.
3. **A reproducibility taxonomy** distinguishing three tiers of Nix-based build: Tier-1 (nixpkgs-source, fully sandboxed), Tier-2 (`__noChroot`-escape for tools needing network or specific devices), and Tier-3 (prebuilt binaries wrapped for runtime use). The taxonomy is documented in the user guide and driven by explicit per-template metadata.
4. **A backing-service abstraction** covering PostgreSQL, MySQL/MariaDB, Redis, and S3-compatible object storage (MinIO, with Garage as a planned alternative). The object-storage addon is built on a pluggable backend interface to permit migration between S3 implementations without application changes. A specific contribution is the MySQL-addon grant logic for Docker-bridge networks (per-host rows for `@'localhost'`, `@'127.0.0.1'`, `@'172.%'`), which mirrors the `pg_hba.conf` pattern already present on the PostgreSQL side.
5. **A structured-diagnostics pipeline**: a `Diagnosis` dataclass replaces bare tracebacks at every major failure point in the deployment pipeline, producing messages of the form `[Component] can't [action]: [reason]. [Hint].`. Runtime diagnostics are collected *before* cleanup destroys the application container, yielding self-contained per-test failure reports without requiring an operator to reconstruct the state manually.
6. **An end-to-end test corpus** of 99 real-application variants (Appendix C) spanning PHP, Node.js, Go, Python, Java, Ruby and Rust across four build strategies (Docker, native uWSGI, hand-crafted Nix, template-generated Nix), running on a remote VPS.

The claims of this report are primarily qualitative and architectural. A quantitative evaluation (§5.5, §7) — control-plane footprint against K3s, Docker Compose and bare uWSGI; deployment latency; Nix closure versus Docker image size — is planned for the final report and peer-reviewed publication later in 2026.

### 1.3 Report Structure

§2 situates Hop3 with respect to related work (container orchestrators, existing PaaS systems, Nix-based deployment). §3 describes the overall system design. §4 covers implementation, organised by subsystem. §5 reports the preliminary qualitative evaluation and lists the measurements that remain outstanding. §6 discusses limitations, design trade-offs, and threats to validity. §7 concludes and lays out future work. Appendices collect the glossary, Nix template reference, application catalogue, and NGI deliverable mapping.

## 2. Background and Related Work

### 2.1 The PaaS Spectrum

Container orchestrators (Kubernetes [1], Nomad, Mesos) are designed for multi-node clusters running workloads that require service discovery, scheduling, self-healing, and rolling upgrades across failure domains. They provide strong guarantees for this case, at the cost of a control plane that is itself a distributed system. Single-node variants (K3s, Minikube, Docker Swarm in single-manager mode) reduce the control-plane weight but inherit most of the operational surface: containers, pods, kubelets, service accounts, RBAC, admission controllers.

At the other end, single-server PaaS systems predate the container era: Heroku's "git-push deploy" model [4] inspired a family of open-source re-implementations, most prominently Dokku [2] and Piku [3]. These systems deploy via buildpacks or simple build-and-run scripts, target a single host, and are operationally much lighter than Kubernetes. Their limitations are (a) a loose reproducibility story (buildpacks resolve dependencies at build time against the network), (b) limited first-class support for backing services beyond what a cooperating operator wires up manually, and (c) ecosystem fragmentation (competing buildpack registries with divergent compatibility matrices).

CapRover [5] and Caprover-like systems sit between these poles: they deploy via Docker, provide a web UI, and offer managed backing services, but inherit the Docker attack surface and image-size footprint.

Hop3 occupies the same slot as Dokku/Piku in terms of operational model (single host, git-push, plugin-extensible) but adds (a) a Nix-based reproducible build alternative to buildpacks, (b) a uniform plugin architecture across builders, toolchains, addons, and proxies, and (c) a structured diagnostics contract. It does not target Kubernetes-style multi-node orchestration.

### 2.2 Reproducibility: Containers Versus Nix

Container images, as produced by `docker build` or equivalent, capture an artefact that is bit-for-bit reproducible *in content* only if every layer in the image is itself content-addressed and every external input (apt repositories, pip indexes, upstream registries) is pinned to a digest. In practice, typical `Dockerfile` authoring violates both preconditions: `apt-get install` fetches whatever is currently in the configured mirror, and `pip install` resolves against PyPI's current state.

Nix [6,7] addresses this by making the build environment itself content-addressed: every input (source code, compiler, system libraries) is identified by a cryptographic hash of its inputs, and the build runs in a sandbox with no network access except to explicitly declared, hash-pinned fetchers. The resulting artefact, in principle, is reproducible given only the pinned nixpkgs revision. The practical caveats around reproducible-builds (timestamps, parallel build non-determinism, compiler nondeterminism) are well documented in the Reproducible Builds project literature [8].

Hop3's Nix integration is a pragmatic instantiation of this approach: we use nixpkgs as the source of truth where possible (Tier-1), use `__noChroot` to permit sandbox escape for specific build tools that cannot operate inside the sandbox (Tier-2, e.g. some JVM-based build systems), and fall back to prebuilt artefacts with a cryptographic hash (Tier-3) where upstream does not publish source-buildable packaging. This taxonomy is the explicit contract exposed to package authors; see Appendix B.

### 2.3 Prior PaaS Systems

The closest systems in operational model are Dokku [2] (Herokuish-based, plugin system, Docker-backed) and Piku [3] (pure Python, no Docker, uWSGI-backed, minimal plugin model). Hop3 is closer to Piku in internal model — uWSGI-managed processes with per-app virtualenvs — but extends the plugin architecture significantly and introduces Nix as a first-class alternative to the uWSGI-only runtime.

Cloud Foundry [9] and its derivatives occupy a larger footprint than Hop3 targets; they require a dedicated multi-component platform installation. They are mentioned here as the original source of the "buildpack" concept that Dokku and Piku inherit.

Unikernel-based systems (MirageOS, Unikraft [10]) and WASI-based systems (Wasmtime, WasmEdge) offer alternative reproducible-deployment routes. They are more radical — they replace the operating system for the application — and have different trade-offs (higher reproducibility, narrower ecosystem). Hop3 can be seen as a "fourth path" alongside containers, unikernels, and WASI: retaining a conventional POSIX runtime while gaining content-addressed builds via Nix.

## 3. System Design

### 3.1 Architecture Overview

Hop3 is a client-server system. The server runs on the deployment target (typically a VPS or a dedicated machine) and exposes a JSON-RPC endpoint over HTTP(S) or over an SSH tunnel. Clients — the `hop3` CLI and the Textual-based `hop3-tui` — parse user commands locally and dispatch RPC calls to the server. All RPC endpoints require authentication; the CLI acquires a JWT token via an explicit login step (password or magic link) and reuses it for subsequent calls.

```
┌─────────────────┐     SSH / HTTPS     ┌─────────────────────────────────┐
│   Workstation   │◄────────────────────►│          Hop3 Server           │
│                 │      JSON-RPC        │                                 │
│  hop3 CLI /     │                      │  Litestar (ASGI)  ←  Pluggy    │
│  hop3-tui       │                      │       │                 │       │
└─────────────────┘                      │  SQLAlchemy ORM   →  plugins   │
                                         │       │                         │
                                         │  SQLite / PostgreSQL            │
                                         │                                 │
                                         │  Nginx / Caddy / Traefik        │
                                         │       │                         │
                                         │  uWSGI process manager          │
                                         └─────────────────────────────────┘
```

Internal components:

- **Litestar** [11] provides the ASGI web framework and exposes the JSON-RPC endpoint.
- **Pluggy** [12] is the plugin host; all extension points are defined as hook specifications (`@hookspec`) and implemented by plugins (`@hookimpl`).
- **SQLAlchemy** with Advanced Alchemy provides ORM access to either SQLite (default) or PostgreSQL for the control-plane database. The control-plane schema stores applications, users, addons, and audit records.
- **Dishka** is used for dependency injection across controller, command, and plugin layers.
- **uWSGI** runs the deployed applications in "emperor" mode, where each application is a vassal managed via its `.ini` file. The emperor handles respawn, graceful reloads, and process limits.

### 3.2 Deployment Pipeline

A deployment is triggered by either `hop3 deploy` (client-driven) or by a `git push` to a bare repository that the server manages on behalf of the application. The pipeline stages, implemented in `hop3/deployers/deployer.py`, are:

1. **Archive upload.** The client ships a source archive to the server; for `git push`, the server receives the tip of the pushed branch.
2. **Configuration parsing.** `Procfile` (if present) and `hop3.toml` (optional) are parsed into an `AppConfig` object. `hop3.toml` precedence rules are documented in the configuration reference.
3. **Builder selection.** The `Builder` protocol's `accept()` method is consulted on each registered builder (LocalBuilder, DockerBuilder, NixBuilder); the first accepting builder is used. Selection can be forced via `[build].builder`.
4. **Toolchain selection.** For LocalBuilder, the `LanguageToolchain` protocol is queried analogously (Python, Node, Go, Rust, Ruby, Java, PHP, generic).
5. **Build.** The toolchain or builder runs in an isolated environment under the `hop3` system user, with a per-app virtualenv or Nix store entry.
6. **Deploy.** The Deployer (uWSGI or Docker Compose or static) takes the build output and launches the process(es). For uWSGI, this writes a vassal `.ini` file under `uwsgi-enabled/`.
7. **Proxy configuration.** The Proxy plugin (Nginx, Caddy, or Traefik, depending on configuration) writes a site configuration reflecting the application's port and any custom routes.
8. **Health check.** The application is probed on its declared health-check path; failures here are reported via a structured `Diagnosis` naming the specific component that refused to respond.

### 3.3 Plugin Model

The plugin architecture is intentionally narrow: a small number of orthogonal protocols cover every extension point.

| Plugin category | Protocol | Representative implementations |
|-----------------|----------|--------------------------------|
| Builder | `accept(app)`, `build(ctx)` | LocalBuilder, DockerBuilder, NixBuilder |
| Language toolchain | `accept(src)`, `setup()`, `build()` | Python, Node, Go, Rust, Ruby, Java, PHP, generic |
| Deployer | `deploy(ctx)` | uWSGI, Docker Compose, static |
| Addon | `provision()`, `destroy()`, `env()` | PostgreSQL, MySQL, Redis, S3 |
| Proxy | `configure(app)`, `reload()` | Nginx, Caddy, Traefik |
| OS implementation | `package_install()`, `service()` | Debian family, Red Hat family |
| Health check | `is_configured()`, `check()` | PostgreSQL, Redis, filesystem, disk |

Plugins register themselves via Pluggy hooks declared in `hop3/core/hookspecs.py`. Core code consults the hook registry and iterates; there is no core-level special case for any concrete implementation. A plugin is a Python package under `hop3.plugins.<category>.<name>`.

### 3.4 Nix Integration

The Nix integration is the central technical contribution of the current project phase (NGI tasks T1 and T2, see Appendix D). It has two entry points:

**Hand-crafted path.** The operator places a `hop3.nix` file in the application repository. The file returns an attribute set `{ package, env }` where `package` is a derivation producing `$out/bin/<wrapper>` and `$out/hop3/runtime.json` (the runtime contract), and `env` is a dictionary of environment variables exposed to the runtime. This path is the most flexible and is used for 23 applications in the current catalogue.

**Template-generated path.** Rather than ask every application packager to write Nix from scratch, we observed that the recurring patterns across hand-written `hop3.nix` files cluster into a small number of templates. Eight templates have been extracted (see Appendix B): `nixpkgs-wrapper`, `prebuilt-binary`, `prebuilt-archive`, `node-prebuilt`, `php-app`, `python-venv`, `java-war`, `ruby-bundler`. Each template is driven by a concise `[nix]` section in `hop3.toml`; the builder materialises the full `hop3.nix` at build time. 20 applications are currently packaged via templates.

The **three-tier reproducibility taxonomy** (Tier-1 nixpkgs-source, Tier-2 `__noChroot`, Tier-3 prebuilt-artefact) is an explicit attribute on each template. `nixpkgs-wrapper` is Tier-1 because it wraps a nixpkgs-built package. `php-app`, `python-venv`, `node-prebuilt` and `ruby-bundler` are Tier-2 because their underlying package managers require network access that Nix's pure sandbox does not permit. `prebuilt-binary` and `prebuilt-archive` are Tier-3. The classification is surfaced in the documentation and is intended to let operators make an informed choice when a given application can be packaged in more than one way.

The **runtime contract** (`$out/hop3/runtime.json`) is:

```json
{
  "workers": { "<role>": "<path to wrapper script>" },
  "env":     { "<name>": "<value>", ... },
  "path":    [ "<path to prepend to $PATH>", ... ]
}
```

This contract is the only surface the Hop3 runtime inspects after the Nix build; the Nix derivation is otherwise opaque to the runtime.

### 3.5 Security Model

The control plane requires authentication on every RPC call; addon credentials are encrypted at rest using Fernet AEAD [13] with a key derived from the server's `HOP3_SECRET_KEY` via PBKDF2-HMAC-SHA256. Password hashing uses bcrypt with cost factor 12. SSH tunnelling is supported for the CLI to avoid exposing the RPC endpoint publicly. A summary of security-audit outcomes is provided in §5.3.

## 4. Implementation

### 4.1 Packages

Hop3 is implemented as a Python monorepo with five packages:

| Package | Role | Key technologies |
|---------|------|------------------|
| `hop3-server` | Control plane running on the target | Litestar, SQLAlchemy, Pluggy, Dishka, uWSGI |
| `hop3-cli` | Client CLI (`hop3`, `hop`) | Python, Click, JSON-RPC |
| `hop3-installer` | Installation toolkit (`hop3-install`, `hop3-deploy`) | Python stdlib only — no runtime deps |
| `hop3-tui` | Terminal UI | Textual |
| `hop3-testing` | Test framework and `hop3-test` CLI | Pytest, Docker SDK |

The `hop3-installer` package deliberately restricts itself to the Python standard library: the installer must run on a freshly provisioned machine before any package manager is available, and is distributed as a single bundled file (see §4.7).

### 4.2 Build and Deployment Subsystems

The build subsystem entry point is `hop3/deployers/deployer.py::do_deploy`. It orchestrates the stages described in §3.2 and is responsible for emitting structured `Diagnosis` objects on failure.

Language toolchains (`hop3/toolchains/*.py`) encapsulate language-specific detection and build logic. The generic detection uses well-known markers: `requirements.txt` / `pyproject.toml` for Python, `package.json` for Node, `go.mod` for Go, `Cargo.toml` for Rust, `Gemfile` for Ruby, `pom.xml` / `build.gradle` for Java, `composer.json` for PHP. Detection can be forced via `[build].toolchain` in `hop3.toml`.

Deployers (`hop3/plugins/deploy/*.py`) are responsible for turning build artefacts into running processes. The uWSGI deployer writes a vassal file under `uwsgi-enabled/` and relies on the emperor to respawn on failure; the Docker Compose deployer generates a per-app `compose.yaml` and runs `docker compose up -d`; the static deployer writes Nginx-served files to a fixed document root.

### 4.3 Nix Templating System

The Nix template registry is in `hop3/plugins/build/nix/gen/templates/`. Each template is a Python class implementing:

```python
class Template(Protocol):
    name: str
    def generate(self, spec: AppSpec) -> str: ...
```

`AppSpec` is a dataclass describing the application-level parameters (version, exec target, environment, addon wiring). The template's `generate()` method emits a complete `hop3.nix` expression as a string.

A safety check at the bundler level (added after a production incident where two plugin modules declared a top-level `_has_systemd()` and one silently shadowed the other) performs an AST-level scan across concatenated modules and refuses to bundle on name collision. This check lives in `hop3-installer/bundler.py` and is explicit about the kind of regression it prevents; it is the kind of infrastructure guardrail that only pays off once but then prevents a class of bug.

### 4.4 Backing Services

**PostgreSQL.** The addon provisions a per-app user, a per-app database, and writes a `pg_hba.conf` entry covering local-Unix, `127.0.0.1`, and `172.16.0.0/12` (the Docker default bridge range). The rationale for the bridge entry is that Docker-based applications running on the same host connect to PostgreSQL through the bridge, not through `localhost`.

**MySQL/MariaDB.** Mirrors the PostgreSQL pattern but must do so through MySQL's per-host grant model. The addon creates three user rows per application — `user@'localhost'`, `user@'127.0.0.1'`, `user@'172.%'` — with identical privileges, and drops all three on teardown. An internal helper (`_create_or_update_user()`) centralises the CREATE-or-ALTER pattern to keep the three-row case consistent.

**Redis.** Connection pool, per-app logical database number, no authentication by default (relies on the loopback bind).

**S3-compatible object storage.** The addon is implemented on a pluggable backend interface (`hop3/plugins/s3/backend.py`) with the MinIO backend shipped in 0.5 and a Garage [14] backend planned. Each application gets a per-app bucket, a dedicated access-key pair with privileges scoped to that bucket, and connection parameters exposed as `S3_*` environment variables. The backend abstraction is a direct response to concerns about MinIO's licensing trajectory.

### 4.5 Reverse Proxy

Three proxy plugins are shipped: Nginx (default), Caddy, Traefik. Each plugin generates a per-app site configuration, reloads the proxy on configuration change, and manages TLS certificates (via Let's Encrypt for Caddy/Traefik by default, via `certbot` for Nginx).

### 4.6 Diagnostic Infrastructure

Two mechanisms in combination address the "why did my deployment fail" question:

**Structured diagnosis.** A `Diagnosis` dataclass with fields `(component, action, reason, hint)` is emitted at every failure point in the deployment pipeline. The rendered form is `[Component] can't [action]: [reason]. [Hint].` — a shape deliberately prescriptive enough that reviewers can spot missing hints during code review. Code paths that previously raised `Abort("deploy failed")` with no context now carry a diagnosis through to the CLI.

**Runtime log collection before cleanup.** The test runner, on failure, calls `collect_runtime_logs()` (in `hop3_testing/runtime_diagnostics.py`) *inside* the same try-block as the test, so the target application's directory, uWSGI worker logs, build log, generated Nginx configuration, generated uWSGI configuration, and Docker container state and logs are captured *before* the session's cleanup step destroys them. The collected context is stashed on the `TestResult` object and written to a per-test log file. The operator no longer needs to SSH into the target to reconstruct failure state.

### 4.7 Installer

`hop3-install` bundles itself into a single file via a bundler (`hop3-installer/bundler.py`) that concatenates module sources with AST-level name-collision detection. The single-file installer is what the curl-to-python one-liner on the project website consumes:

```
curl -LsSf https://hop3.cloud/install-server.py | sudo python3 -
```

Two install modes are supported: single-user (Nix installed under the user's home, no daemon) and multi-user (Nix daemon under systemd or supervisord). Init-system detection uses `/proc/1/comm`, an unambiguous and init-agnostic check on Linux.

## 5. Preliminary Evaluation

The evaluation presented here is **qualitative and architectural**. It documents the reach of the packaged-application corpus, the state of the test infrastructure, and the outcomes of an internal security audit. Quantitative measurements (control-plane footprint, deployment latency, Nix closure versus Docker image size) are explicitly deferred to the final report (§7).

### 5.1 Application Coverage

**99 real-application deployments are validated end-to-end** on a remote VPS, covering 20+ distinct open-source applications in four build-strategy variants (Docker, native uWSGI, hand-crafted Nix, template-generated Nix). The application mix spans CMS and publishing (WordPress, Ghost, BookStack, Wiki.js, HedgeDoc), collaboration (Etherpad, CryptPad, NextCloud), project management (Kanboard, Focalboard, Vikunja), developer tooling (Gitea, Jenkins, Grafana, Mattermost), analytics and surveys (Matomo, LimeSurvey, Easy Appointments), ERP/CRM (Dolibarr, Invoice Ninja), federation (Matrix Synapse, Isso, Mastodon), and utilities (Adminer, Miniflux, Listmonk, SearXNG, Radicale). Appendix C gives the full catalogue with per-variant coverage status.

Two applications are **explicitly deferred** with documented blockers: **Monica** (Laravel Mix / webpack 5 incompatibility, resolved upstream only in Monica v5 which moves to Vite) and **SonarQube** (bundled Elasticsearch crashes without kernel-level `vm.max_map_count` tuning, outside the PaaS scope). The decision to surface these publicly in an `apps/bad/` directory with per-app `DEFERRED.md` notes is deliberate: silent gaps are a form of unaddressed debt, and an explicit blocker record invites community contribution and third-party verification.

### 5.2 Test Infrastructure

The test corpus has four layers:

| Layer | Count | Scope |
|-------|-------|-------|
| Unit | ~680 | Individual functions, classes, parsers, regex helpers |
| Integration | ~240 | Component interaction (ORM, plugin loading, RPC dispatch) |
| System | ~25 | Full app with CLI against a Docker-hosted Hop3 instance |
| End-to-end (real-app) | 99 | Full deployment workflows across Docker/native/Nix variants |

Unit and integration layers run on every commit; system and end-to-end layers run nightly and on release branches. Cumulative test count is 943 unit + integration + installer tests plus the 99 end-to-end real-app deployments. The end-to-end suite produces per-test diagnostic log files with the material described in §4.6; a single test run is self-sufficient for post-mortem analysis.

### 5.3 Security Audit Findings

An internal audit during Q1 2026 produced the following findings and fixes (milestone M3.8, code portion complete):

| Finding | Status | Mitigation |
|---------|--------|------------|
| JWT token tampering | Fixed | Signature verification enforced on every request |
| SQL injection | Fixed | Parameterised queries throughout |
| Hardcoded passwords in examples | Fixed | Removed; operators must set `HOP3_SECRET_KEY` |
| Authentication bypass on non-public routes | Fixed | Middleware validates tokens on all non-public routes |
| Plaintext credential storage | Fixed | Fernet AEAD with PBKDF2-HMAC-SHA256 key derivation |
| Magic-link default username | Fixed | `default="admin"` removed from the CLI |
| Bearer-token case sensitivity | Fixed | Case-insensitive match per RFC 7235 [15] |
| Session lifetime not configurable | Fixed | `HOP3_TOKEN_EXPIRY_HOURS` environment variable |
| No rate limit on authentication endpoints | Fixed | In-memory sliding-window limiter (5 req/min per IP) on `/auth/login` and `/auth/magic/{token}` |

An **external security review** is scheduled for release 0.6. The internal findings and regression tests above will be shared with a third party for validation before the final report.

### 5.4 Reproducibility Tiers in the Packaged Corpus

Of the 43 Nix-packaged application variants (23 hand-crafted + 20 template-generated), the tier distribution is approximately:

- **Tier-1 (nixpkgs-source):** Go- and Rust-based applications available in nixpkgs (Miniflux, Gitea, Grafana, Mattermost, Wiki.js, Vikunja). Fully reproducible within the nixpkgs-revision contract.
- **Tier-2 (`__noChroot`):** PHP, Python-venv, Node-prebuilt, Ruby-bundler templates; these require network access to a package manager that the strict Nix sandbox does not permit.
- **Tier-3 (prebuilt-archive or prebuilt-binary):** Applications where upstream does not ship source-buildable packaging, or the build is prohibitively heavy for a per-deployment rebuild.

The tier is surfaced in the documentation and in the template metadata, so operators and auditors can reason about the reproducibility guarantees of a given deployed application.

### 5.5 Limits of the Current Evaluation

The following measurements are **not yet available** and are targeted for the final report:

- **Control-plane memory and CPU footprint** compared to K3s, Docker Compose, and bare uWSGI under equivalent workloads.
- **Deployment latency** from `git push` to first healthy response, broken out by build strategy (Docker, native, hand-crafted Nix, template-generated Nix).
- **Nix closure size** compared to equivalent Docker image size, including delta-transfer bandwidth savings when upgrading an application.
- **Application cold-start latency** under uWSGI emperor mode.
- **Reproducibility-in-practice:** bit-for-bit hash comparison across two independent rebuilds of each Tier-1 application in the corpus.

These will be collected on a dedicated benchmark harness on the 99-variant corpus; the methodology will be documented in the final paper.

## 6. Discussion

### 6.1 Design Trade-offs

Hop3 deliberately does not support multi-node orchestration, distributed scheduling, or cross-host service discovery. An operator needing those properties should use Kubernetes or Nomad; Hop3 targets the complement of that population. This is a positioning choice, not a limitation of the underlying design: the plugin architecture would accommodate a multi-node scheduler, but doing so would require rewriting the deployment pipeline around a consensus layer and would lose the single-process-control-plane simplicity that is the system's main advantage.

The decision to offer **both** a uWSGI native path and a Nix path reflects the observation that Nix is the right default for reproducibility but uWSGI is the right default for familiarity. An operator running a handful of Python Flask applications with a PostgreSQL database benefits little from Nix; an operator packaging a heterogeneous application catalogue benefits greatly. Supporting both doubles the test matrix but avoids forcing a choice the system does not need to force.

### 6.2 Threats to Validity of the Qualitative Claims

**Packaged-application coverage as a proxy for general capability.** The claim that Hop3 deploys 20+ real open-source applications is a coverage claim, not a quality claim. It demonstrates that the plugin architecture is expressive enough to cover a real ecosystem, but it does not measure whether operators can operate these applications in production with the reliability and latency profiles they need. Production-validation data is explicitly out of scope for this interim report and is scheduled for M4 in release 0.6.

**Security-audit completeness.** The internal audit found and fixed nine concrete issues but was not conducted under third-party threat modelling. Classes of vulnerability that are typical in PaaS systems — tenant isolation failures, privilege escalation across addons, configuration-parser-driven command injection — may remain. The planned external review is the mitigation.

**Evaluation corpus selection bias.** Applications in the corpus were selected for strategic fit with the project's sovereignty positioning, not uniformly. The corpus is therefore representative of applications that matter to the target user communities (SMB, non-profit, educational, municipal) but not necessarily of the application ecosystem at large.

### 6.3 Limitations Specific to the Nix Integration

The eight templates cover the packaging patterns observed in the current catalogue, not all patterns in general. Applications built from unusual source layouts, applications requiring complex multi-stage builds, or applications whose build produces multiple deployable artefacts will still require hand-written `hop3.nix`. The template system does not replace Nix expertise; it reduces the amount of Nix expertise required for the common case.

The `__noChroot` escape in Tier-2 templates permits the build to deviate from strict reproducibility in exchange for the ability to package applications whose upstream build system cannot operate in a pure Nix sandbox. This is a pragmatic compromise; operators who require strict Tier-1 reproducibility can inspect the template metadata and choose accordingly.

## 7. Conclusion and Future Work

This report has described Hop3, a plugin-based PaaS for single-server deployment, at the state of April 2026. The principal contribution of the reported period is the completion of the Nix integration (tasks T1 and T2 in the NGI deliverable taxonomy), including an eight-template code-generation system, a three-tier reproducibility taxonomy, and a runtime contract that decouples the Nix derivation from the Hop3 runtime. The S3-compatible object-storage addon, the MySQL per-host-grant logic, the structured `Diagnosis` pipeline, and the per-test runtime-log collection are further contributions that enabled the end-to-end validation of 99 application-variant deployments across 20+ real open-source applications.

The evaluation reported here is qualitative. **The work remaining for the final report** consists of:

1. **Quantitative benchmarking** against K3s, Docker Compose, and bare uWSGI (control-plane footprint, deployment latency, closure/image size, cold-start latency, reproducibility-in-practice). A dedicated benchmark harness will be developed for this.
2. **Multi-service application support** per ADR 038: the current `[run.workers]` model handles same-process-tree workers, but multi-component applications (Mastodon Rails+Sidekiq+Node, NextCloud web+cron, AppFlowy with its microservice stack) need per-component resource limits, per-component health checks, and independent scaling. Phase 1 (schema) is scheduled for release 0.6; Phase 2 (runtime) for 0.7.
3. **External security audit** (scheduled for 0.6). The internal audit outcomes in §5.3 will be shared with a third party for validation.
4. **Operational hardening:** firewall/WAF integration (M3.5), web UI (M3.7), screencasts (M5.6), production validation under the M4 milestone.
5. **Peer-reviewed publication** summarising the architecture and the quantitative evaluation.

A companion paper is in preparation for submission to a systems venue; it is narrower in scope than this report and focuses on the Nix integration and the reproducibility taxonomy.

## Appendix A — Glossary

| Term | Definition |
|------|------------|
| **Addon** | A backing service (database, cache, object storage) provisioned and managed by Hop3 on behalf of deployed applications. |
| **Builder** | A plugin that orchestrates the build of an application, selecting a language toolchain or a dedicated build path (e.g. Docker, Nix). |
| **Deployer** | A plugin that turns build artefacts into running processes (uWSGI vassals, Docker containers, static files). |
| **Toolchain** | Language-specific build logic, used by the LocalBuilder when a matching language is detected. |
| **Proxy** | A reverse proxy routing HTTP(S) traffic to deployed applications (Nginx, Caddy, or Traefik). |
| **Diagnosis** | A structured error record `(component, action, reason, hint)` emitted at every failure point in the deployment pipeline. |
| **Runtime contract** | The `$out/hop3/runtime.json` file a Nix derivation must produce to be runnable by Hop3. |
| **Tier-1/2/3** | The reproducibility taxonomy for Nix-packaged applications: fully sandboxed (1), `__noChroot` escape (2), prebuilt artefact (3). |

## Appendix B — Nix Template Reference

| Template | Purpose | Tier |
|----------|---------|------|
| `nixpkgs-wrapper` | Wraps an existing nixpkgs package (no source fetch) with a Hop3 runtime wrapper | 1 |
| `prebuilt-binary` | Fetches a single pre-built binary (single file, optional chmod +x) | 3 |
| `prebuilt-archive` | Fetches a pre-built tarball or zip and copies files per a file-mapping spec | 3 |
| `node-prebuilt` | Fetches a Node application (npm-installed) or a Node runtime wrapping a local source | 2 |
| `php-app` | PHP (via nixpkgs) with composer, optional artisan/builtin serve, web-root selection | 2 |
| `python-venv` | Python virtualenv with pip install | 2 |
| `java-war` | JVM (via nixpkgs) running a Servlet WAR | 3 |
| `ruby-bundler` | Ruby with bundler install | 2 |

Each template accepts an `AppSpec` dataclass (see `hop3/plugins/build/nix/gen/spec.py`) and emits a full `hop3.nix` expression. Template selection is driven by `[nix].template` in `hop3.toml`.
