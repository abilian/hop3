# v0.6 — hop3-rootd systemd hardening & relocation (debt)

**Status:** deferred to v0.6. In v0.5 the `hop3-rootd` systemd unit ships with
**minimal sandboxing** (a plain `Type=notify` root daemon + socket activation),
matching the proven-working container/supervisor model. This document records
*why* the heavy hardening was removed, the empirical findings, and the work to
redo it properly.

Related: ADR 041 (privileged-operations agent), §10 (no hop3→root escalation),
§14 (distribution/install).

## Background

`hop3-rootd` is the privileged executor. It runs as root and shells out to
**three** external tools, each with very different filesystem/capability needs:

- **nft** — firewall rules. Needs `CAP_NET_ADMIN`, `AF_NETLINK`. (The original
  hardening was designed around *this* tool, minimally.)
- **nginx** — `nginx -t` (validate) and `nginx -s reload`. `-t` opens nginx's
  `www-data`-owned error log, the pid file, temp dirs, and reads the app vhost
  configs under `/home/hop3/nginx`.
- **systemctl** — `systemctl reload nginx` (talks to systemd over `/run`).

A systemd unit's sandbox applies to **all child processes**, so the hardening
designed for nft also constrains the nginx/systemctl subprocesses.

## What went wrong (empirically established on a real systemd host)

The daemon had **never started on a systemd host** — it crash-looped ~1620
times — so none of the hardening was ever exercised. Once it was fixed enough to
start, the hardening broke the nginx role on three independent axes:

| Directive | Symptom | Cause |
|-----------|---------|-------|
| `ProtectHome=true` | `status=203/EXEC` (daemon never execs) | The venv binary's shebang interpreter `/home/hop3/venv/bin/python3` is under `/home`, which `ProtectHome=true` turns into an empty tmpfs in the unit namespace → kernel can't resolve the interpreter at `execve`. |
| `ProtectSystem=strict` | `nginx -t` → `[emerg] ... failed (30: Read-only file system)` on `/run/nginx.pid` (and `/var/log/nginx`) | `strict` makes everything outside `ReadWritePaths` read-only, incl. `/var/log/nginx`, `/var/lib/nginx`, `/run`. |
| `CapabilityBoundingSet=CAP_NET_ADMIN` (drops `CAP_DAC_OVERRIDE`) | `nginx -t` → `[emerg] ... failed (13: Permission denied)` on `/var/log/nginx/error.log` | rootd runs `nginx -t` as root but **without** `CAP_DAC_OVERRIDE`, so it can't open nginx's `www-data`-owned error log (DAC, not a RO mount). |
| `ProtectHome=*` (any) | `nginx -t` validates the *wrong* config | App vhost configs live in `/home/hop3/nginx`, hidden by ProtectHome → `include /home/hop3/nginx/*.conf` matches nothing. |

Notes:
- `nginx -s reload` **works** via `systemctl` even under the sandbox (systemd
  performs the reload outside the unit's namespace). Only the in-process
  `nginx -t` *validate* is the problem.
- **Test-harness blind spot:** the system test's HTTP check hits the app's
  **direct port**, not the nginx vhost. So uWSGI apps "passed" even though their
  vhosts never applied (rootd's `nginx -t` failed and the uWSGI deploy path
  swallows proxy errors). Only the static app — which has no direct port —
  surfaced the failure. v0.6: also test via the vhost hostname so proxy
  regressions are caught.

## Separately: hop3→root escalation (HIGH, from the security audit)

rootd executes its interpreter + code from `/home/hop3/venv`, which is **owned
and writable by the unprivileged `hop3` user**. A compromised `hop3` can
overwrite that code and trigger a restart → root RCE with `CAP_NET_ADMIN`. This
is exactly the escalation ADR 041 §10 was meant to eliminate (its reference unit
installs to a root-owned `/opt`). `BindReadOnlyPaths` only protects the namespace
*view*, not the host source — it does **not** fix this.

## v0.6 work (prioritized)

1. **Relocate rootd out of `/home` into a root-owned tree** (e.g.
   `/opt/hop3-rootd` with its own venv, `root:root`, not writable by `hop3`).
   Fixes the escalation **and** lets `ProtectHome=true` work as written.
   Touches: `install_rootd_package` (install as root into the new venv, not via
   `su - hop3`), `_resolve_daemon_command` candidate order, `constants.py`, and
   the demo/supervisor path (`demos/lib/backends/docker.py` runs
   `/home/hop3/venv/bin/hop3-rootd`). Re-validate on systemd **and** container.

2. **Redesign the sandbox, tested against all three tools.** Validated building
   blocks from the v0.5 investigation:
   - `ProtectSystem=full` (keeps `/usr`,`/etc` RO; `/var`,`/run` writable for
     nginx logs/pid/temp + systemd) — or `strict` + explicit
     `ReadWritePaths=/var/log/nginx /var/lib/nginx /run`.
   - For the nginx configs in `/home/hop3/nginx`: either relocate them too, or
     `ProtectHome=read-only`, or `ProtectHome=tmpfs` +
     `BindReadOnlyPaths=/home/hop3/nginx` (and ensure that dir exists before the
     unit starts).
   - For `nginx -t`'s DAC problem: prefer **not** granting `CAP_DAC_OVERRIDE`.
     Investigate running validate as `nginx -t -e /dev/stderr` (redirect the
     error log) so it never touches the `www-data` log — UNVERIFIED, must test.
     Fallback: add `CAP_DAC_OVERRIDE` (broad; document the trade-off).
   - Re-add, **each re-tested against an actual `nginx -t` + nft rule + reload**:
     the kernel-surface protections, `RestrictAddressFamilies`,
     `MemoryDenyWriteExecute`, the seccomp `SystemCallFilter`, resource limits
     (`MemoryMax`/`TasksMax`/`LimitNOFILE` — the old `16`/`1024` may be too tight
     for the nginx subprocess), `PrivateTmp/Devices/Mounts`.

3. **Add a system test that starts rootd under the real unit** and performs a
   real nginx validate+reload + an nft rule, so the sandbox is exercised in CI
   (it never was — that's how this shipped broken).

The current minimal unit + its guard test (`test_rootd.py::
test_service_template_is_minimal_pending_v06_hardening`) deliberately fail if a
breaking directive is re-added without this redesign.

## Also deferred (unrelated)

- **`HOP3_SECRET_KEY` has two sources — make it a single source of truth.** The
  JWT signing secret is read by the *running service* from `/etc/default/hop3`
  (systemd `EnvironmentFile`, env wins in the config loader) but by any
  **SSH-invoked `hop3-server` CLI** (e.g. `hop3 login --ssh` → `admin:token`, run
  as `su - hop3`, which can't read the 0600 root-owned `/etc/default/hop3`) from
  `hop3-server.toml`. The installer reconciles them today (`write_server_config`
  overwrites the toml with the same secret that went into `/etc/default/hop3`,
  *after* `hop3-server setup` generated its own), so a clean install matches —
  but it's fragile: any partial/interrupted install, or a path that updates one
  store but not the other, silently breaks all freshly-minted tokens (login
  reports success, every RPC then 401s). v0.6: one canonical secret store read
  identically by the service and the CLI (e.g. always read `/etc/default/hop3`,
  or make the toml the sole source and have systemd load it). Symptom seen
  2026-06-04 on a heavily-churned hop3.dev (rebuilt by the cloud test + many
  reinstalls); could not be isolated live because the box was being reprovisioned
  (SSH host key changed). Quick on-host triage when it recurs:
  `diff <(grep HOP3_SECRET_KEY /etc/default/hop3) <(grep HOP3_SECRET_KEY /home/hop3/hop3-server.toml)`
  — if they differ, that's the bug.
- **The deployer didn't upload `hop3-rootd`** (only `hop3-server`) — fixed in v0.5
  (`deployer/deploy.py::_upload_rootd_package`); the cloud test only surfaced it
  because a freshly-rebuilt server has no leftover `/tmp/hop3-rootd`. Keep an eye
  out for other deploy paths that assume leftovers.
- **demo08 / `110-flask-gunicorn-poetry`** — the Python toolchain doesn't
  support a Poetry-managed `pyproject.toml` without a committed `requirements.txt`
  (errors: "Poetry is not detected by the Python toolchain"). Either detect
  Poetry and `poetry export` at package time, or document the requirement. Log in
  `local-notes/stacks-and-apps/DEFERRED-APPS.md` as a toolchain gap.
