## Dependency management

- **Re-record directus-nixgen's `node-deps-hash` on an x86_64 box.** The pnpm store no longer carries `v10/projects` (2026-10-04), so every recorded store hash changed; directus is the only catalog recipe on node-pnpm-install, and its store holds Linux-x64 binaries, so the arm64 Docker target cannot record it. Read the `got:` from a build on the remote target and publish.
- **Pin runtime dependencies.** `hop3-server` (and the other workspace packages) still use loose floors like `litestar[standard]>=2.22.0`. Hop3 is an application. Applications pin their runtime deps to exact versions, with controlled bumps. This avoids two failure modes seen in production: (1) pip's `only-if-needed` upgrade strategy leaving stale transitive deps on the server (e.g. litestar 2.18 satisfying `>=2.18.0` while local code uses 2.22-only APIs), and (2) silent drift between developer machines and the production server.

  Likely shape: `requirements.lock`-style file generated by `uv pip compile` (or `uv lock` with `package = true` flipped), used by the installer's pip step and pinned at PR time.

  The seven-day cooldown (2026-09-23) bounds how new an unpinned dependency can be on a server. It is not a pin, and two installs a month apart still resolve differently.

  Scoped to 0.5 release prep originally and never done; carried as an open box in [`plans/plan-0.7.x.md`](plans/plan-0.7.x.md).

## CLI

- **Add `hop3 validate`.** A local, client-side lint of a project's `hop3.toml`: run the server's schema validation (`ContextSection`, the committed-credential tripwire, field/host-safety checks) on the file at/above the CWD and exit 0/non-zero with no server required, so it can gate CI. Top-level and project-rooted, the dry sibling of `hop3 deploy` (no `--app`; the app comes from `[metadata].id`). Renamed from the obsolete `hop3 config validate` idea, which clashed with the `config`→`env` alias (ADR 036 D17). Original intent: ADR 001 §Consequences, ADR 027 §Developer Experience. (ADR 027 also lists a stale `hop3 config show` / `config export` from the same wishlist. Revisit if those are still wanted.)

  A checker already exists. `hop3check`, shipped from the `letscode-plugins` repo, is the one the packaging skill tells people to run. It implements the same rules by hand. It reports clean on recipes the server then refuses at deploy time. Since the php-fpm migration it also reports `nothing-to-run` on every PHP recipe, which is now the correct shape for one. The drift runs both ways, so whichever side is right on a given rule, two hand-written implementations of one contract will keep disagreeing. Whatever ships here should validate against the published `schema/hop3.toml.schema.json`, so the file holds one implementation.

- **`--` does not survive flag parsing.** `parse_flags` consumes the POSIX end-of-options marker (`_END_OF_FLAGS` in `commands/flags.py`) and records nothing about where it was, so a later pass cannot tell an escaped flag from one of ours: `hop3 apps -- --help` still reads as a request for hop3's own help. The `run` boundary has the same shape and is handled (`app_scope.RunBoundary`, fed by both passes); `--` needs a change to what `parse_flags` returns, which is why it was not folded in with it.

- **`hop3 login --token <token>` puts a secret on argv**, where `ps` can read it for the length of the call. ADR 036 gives `user add`, `user set-password` and `auth get-token` the `KEY=-` / `KEY=@file` / hidden-prompt treatment; the `--token` path never got it. The deployer is a caller (`deployer/deploy.py`, whose own comment at the call notes there is no stdin form to use). Small, and the rewriting machinery already exists in `commands/arguments.py`.

The items below come out of the 2026-09-25 pass that lined the client's argument handling up with the server's (see "Two Parsers Read One argv" in [`lessons-learned/cli-ergonomics.md`](lessons-learned/cli-ergonomics.md)).

- **The `waf` commands take the app as a positional.** `waf logs [<app>]`, `waf bans list [<app>]` and `waf bans clear <app> [<ip>]` break ADR 036 D5 (the app is always `--app`), so `hop3 waf logs --app x` is refused by the client and a project's ambient app is never used. Move them to `--app`: an optional filter for `logs` and `bans list` (the `_EXPLICIT_ONLY` set in `hop3_cli/core/app_scope.py`), app-scoped for `bans clear`. Keep the positional working behind a deprecation for a release. Once they read `--app`, the guard in `test_app_scope_matches_server.py` checks them like every other command.

- **Delete the RPC `git-hook` command, or find its caller.** `commands/git.py` `GitHookCmd` duplicates `hop3-server git-hook` (`server/cli/git.py`), which is what the post-receive hook runs. The RPC version reads the server process's stdin, so over RPC it can only answer "No push data received". The guard test exempts it by name (`NOT_SENT_BY_THE_CLIENT`); the exemption goes with it.

- **Most client messages still wrap at 80 columns when piped.** Rich word-wraps at the console width, which is 80 when the output is not a terminal. `print_text`, `print_summary` and `print_error` pass `soft_wrap=True`; warnings, info, success, progress and log lines do not, so a script reading them gets hard newlines mid-sentence. One setting on both consoles (`Console(soft_wrap=True)`) would cover them all, once tables are checked to lay out the same.

- **`hop3 app logs` has no follow mode.** Nine tutorials reached for `--tail`, which it never had; they now show the last 100 lines. Following a running app's log (streamed, like `hop3 deploy`'s output) is what they wanted.

- **Decide whether a no-op addon command succeeds.** `hop3 addon destroy x --type redis` for an addon that does not exist answers "does not exist" as plain text and exits 0, and `hop3 addon detach` of an addon that is not attached does the same. That can be idempotence (`rm -f`) or a silent failure; whichever it is, the help should say so and the exit code follow.

- **`hop3 system status` exits 0 on warnings.** Its help said a warning exits non-zero; the client only fails on an error item, so the help now says "when any check fails". If a degraded server should fail a script's check, the server has to say so explicitly (a distinct item or exit code), not the help.

- **Check the scripting examples in `docs/src/guides/cli-migration.md`.** They pipe `hop3 backup list --app myapp --json` into `jq -r '.data[].id'`, but `--json` prints the list of response elements (here one `table`), not a `{"data": [...]}` object. Unverified against a server; the docs guard checks the command line, not what a pipe does with its output.

- **Some ADRs name commands that were never built.** The docs guard skips ADRs, because they record proposals: ADR 031 (`hop3 blueprints ...`), ADR 032 (`hop3 releases`, `hop3 rollback <app> [<version>]`), ADR 036 (`hop3 env set --from-file -`, `hop3 backup download <id>`). Where the design settled on other names (`app rollback --app`, `catalog install`), the ADR should describe it with those, so a reader does not take a dropped spelling for the CLI.

## Testing

- **The redeploy check proves the app comes back, not that its data does.** listmonk's recipe ran `--install --yes` on every deploy, which wipes its tables, and passed the redeploy check: the test had created nothing, so there was nothing to lose. The same goes for a secret regenerated at deploy time (writefreely, hedgedoc, monica): the validations sign in afresh and pass. A check that writes something through the app before the redeploy and reads it back after would catch both. It needs a per-recipe action, which `check.py` could carry the way it already carries the sign-in.

- **A deploy whose uWSGI config is refused reports a timeout.** In the e2e image (whose uWSGI has no Python plugin) a `wsgi:` worker's vassal is refused at once, `[strict-mode] unknown config directive: virtualenv`, and the emperor curses and throttles it. The deploy waited its full 60 s, then said the app "did not respond to health checks" and suggested raising `start-timeout`. The emperor's own words were in its log the whole time; the readiness diagnosis should read them (the Lessons Checklist already says to detect crashes from the process manager's words).

- **Real apps behind the access gate run only on a server with an admin domain.** `180-flask-gated` needs one, and the runner leaves it out on a server without, listed with its reason in every report: the Docker target, and a remote server addressed by IP. The catalog runs address their box by IP and select by status, so neither picks it up. Where the gate should run regularly is undecided: target the box by its hostname and include the fixtures, or give the harness's Docker and IP targets an admin domain of their own.

- **The Docker e2e target lets two sessions share one container without either knowing.** The target has a fixed container name (`hop3-server-test`) and fixed ports, so a second `pytest packages/hop3-server/tests/c_e2e/` started while one is running tears the container down and re-installs it under the first. Neither session is told. The result is a corrupt failure: each run sees the other's server restarts, addons and database rows.

  Observed 2026-09-11 with two sessions live at once. Seen from inside, every symptom had the same cause. `RemoteDisconnected` / `Connection refused` meant the other session was restarting hop3-server. `Authentication required` (exit 4) and `The server redirected the RPC call to /rpc/` meant a server had restarted under a live client. An nginx reload reported "no fresh worker processes appeared within 15s" because hop3-rootd, which performs that verification, was itself restarted mid-verify. `test_list_and_filter_backups` failed because `hop3 backup list` returned **the other session's app** and none of its own.

  `notes/lessons-learned/deployment-diagnostics.md` already says one e2e session per machine and that a failure seen while another session was active is not evidence. The harness does not enforce it. **Fix shape:** the Docker target should detect that the container is already owned by a live session (a lock file carrying the owning PID, or a label written at start and checked before teardown) and abort with a message naming the owner. A session that steals a running container breaks the "no silent fallback" rule, here in the test harness itself.

- **`--clean` does not clean the named volumes, so a poisoned download cache survives a blank-slate rebuild.** mediawiki failed nine times with `tar: Unexpected EOF`, identically across runs that were supposed to share no state, because `hop3-download-cache` held a 45 MB entry for a 116 MB tarball dating from 2026-08-24. `--clean` replaces the container and leaves the volumes, which is usually what you want and is exactly wrong for a cache. A truncated entry there is indistinguishable from an upstream fault. It is also the one piece of state that makes a failure look reproducible when it is not. mediawiki passes on a remote target, which finally separated the two. **Fix shape:** validate a cache entry on read (size against the recorded `Content-Length`, or a checksum when the recipe gives one) and evict a short file; separately, say in `--clean`'s own output which state it is not clearing.

- **The e2e image build fails intermittently on apt.** `E: Sub-process /usr/bin/dpkg returned an error code (1)` while installing the 25-package catalogue baseline, with a .NET 9 install failure beside it (since removed: the platform installs SDKs 8 and 10); the run dies in fixture setup before any test. Not disk (host and Docker VM both had >17 GiB free). Seen 2026-09-11, under the same two-session conditions as above, so re-confirm on a quiet machine before chasing it.


- **The tutorial suite has no scheduled run.** It could not pass on the Docker target for four months and nothing said so; a nightly or pre-release run of `hop3-test run docs/tutorials/` would have. `make test-tutorials` still runs the old `scripts/run-all-tutorials.py`, which deploys to whatever the caller's default CLI context points at: retire it, or make it call `hop3-test`.
- **Whether Caddy strips a forged `X-Hop3-User` on a gated app's include file is unconfirmed.** nginx refuses an include that forwards requests on a gated app (2026-10-07); Caddy's `forward_auth` may cover it, depending on its handler order. An e2e sending a forged header to a gated app under Caddy, through `CADDY_INCLUDE_FILE`, would settle it.

## Packaging

- **A recipe can pin its Node version but not its package manager.** `[build].node-version` installs an exact Node into the app's venv; pnpm was whatever the host happened to have. Etherpad's `download.sh` carries three separate workarounds for successive pnpm behaviour changes (`auto-install-peers` moving out of `.npmrc`, dependency build scripts needing `dangerouslyAllowAllBuilds`, and `pnpm ls --no-production` being removed, which is fatal at *startup* because upstream's plugin migration calls it). Each was written blind against whatever pnpm was current that week.

  **The server-wide half is done (2026-09-14):** the installer pins an exact pnpm and reconciles it on every run, so the version stops moving under deployed apps and two servers of the same Hop3 version agree. Two questions remain. An app needing a pnpm other than the server's still has no way to ask for one (the *per-app* pin). The package-manager *selection* question (dispatch from the lockfile) is separate. Both scheduled as sub-items under [`plans/plan-0.8.md`](plans/plan-0.8.md) headline 4; neither is urgent now that the drift is stopped.

  **A third axis, found on 2026-09-21: the Nix path uses neither.** `node-pnpm-install` runs whatever pnpm the recipe's pinned nixpkgs carries (9.15.9 for the one recipe on that template), so the installer's server-wide pin does not reach it and `[build].node-version` says nothing about it. The versions differ in behaviour that matters: pnpm 9's `fetch` compiles native addons while populating the store, 11's does not. Whatever answers the per-app question has to answer it for the Nix builder too, or the two builders will keep resolving the same recipe differently.

- **Found by the 2026-09-28 survey of where apps write, not yet checked on a running app.** Each is inferred from a recipe or from a framework's defaults; the runtime-write check and the redeploy in `hop3-test` will confirm or clear most of them.
  - **Gitea and Forgejo rewrite the control plane's `authorized_keys`.** Every app runs with `HOME=/home/hop3`, and both manage `~/.ssh/authorized_keys` for the user they run as. `DISABLE_SSH` is not enough: `SSH_CREATE_AUTHORIZED_KEYS_FILE` defaults to true, and a start whose config or binary path changed (every first deploy; every upgrade) replaces the file through a `.tmp` and a rename. Gitea keeps the lines it did not write, so Hop3's git-push keys survive, but a key Hop3 adds during that window is lost. The six gitea/forgejo recipes now set both keys. What remains: a per-app `HOME` (plan-0.8 headline 1, step 2) fixes the class; until then the harness could compare `authorized_keys` before and after each app's deploy, which would have caught this where the `src/` check cannot. **Fixed by class, 2026-09-30:** every app's processes run with their own `HOME` (`<app>/home/`), so no app reaches the control plane's `~/.ssh`. Build steps still run with the server's `HOME` until builds leave the `hop3` user (plan-0.8 headline 1, step 3).
  - **Fixed names in `/tmp` collide between apps and deploys**: dolibarr's `/tmp/dolibarr-step{1,2,5}.out`, piwigo's `/tmp/piwigo-install.out`, sonarqube's `/tmp/sonarqube.zip`. With per-app users, the sticky `/tmp` turns a collision into a failed deploy. `mktemp`, or a per-app `TMPDIR`. **2026-09-30:** each app now has its own `TMPDIR`, and the dolibarr (three variants) and piwigo bootstraps write under it; sonarqube's is a build step, which keeps the shared `/tmp` until step 3.
  - **A PHP document root is made world-readable** (`run/served_tree.py`, `a+rX`) so nginx can serve its files. That includes WordPress's `wp-config.php` and its database password, readable by every local user. The web server needs the static files, not the PHP sources.
  - **Recipe bugs:** paheko-nixgen's comment says `data/` is on a volume and none is declared; vikunja-nix reads a `.jwt-secret` nothing creates; both mattermost recipes regenerate `AtRestEncryptKey` on every start. **Fixed, 2026-09-29,** with the beta Nix pass, which found more of the kind: three recipes carried an `APP_KEY` written into the recipe (the same key on every install), vikunja-nixgen set no JWT secret, both generated forges put `JWT_SECRET` under `[security]` where it is not read, and first-run markers kept in `src/` re-ran installs on every redeploy.
  - **uv installs without bytecode.** The Python toolchain's `uv sync` has no `--compile-bytecode`, so a uv-built app compiles into its venv at runtime, which a read-only venv would silently stop.
  - **Nextcloud apps from the app store land in `apps/`,** beside the ones Nextcloud ships, and a deploy deletes them while `config.php` still lists them. Upstream's answer is a second, writable `apps_paths` entry (`custom_apps/`) on a volume.
  - **Mattermost's System Console settings do not survive a deploy.** `scripts/setup-config.sh` writes `config.json` from the platform's values on every deploy, by design, so what an administrator changes in the console is overwritten. Mattermost can keep its configuration in the database (`MM_CONFIG` set to the DSN).
  - **`hop3check` reports `no-port` for a recipe whose `[run].start` is a script** that reads `$PORT` itself (keycloak, mattermost). The rule reads the start line only.

- **Left from the native alpha pass, 2026-09-29.** State, secrets and destructive steps are fixed in 20 recipes; these remain:
  - owncast serves its admin with upstream's default password (`abc123`), stored in its database. Setting it at start takes a password on argv; the way through is a post-start hook that changes it over the admin API when the default still works.
  - matrix-synapse's `SERVER_NAME` is `localhost`, and it is the server's permanent identity on the federation: it has to be the public host before the first deploy, and cannot change after.
  - writefreely has no administrator and closed registration, so nobody can sign in; `--create-admin` takes the password on argv.
  - hedgedoc lets anyone create and edit notes (`allowAnonymous`, `defaultPermission: freely`).
  - grafana now has a generated `secret_key`; an install made before it encrypted its datasource credentials under the published default, and they need entering again.
  - Build caches still land in the control plane's home (`~/.cargo`, `~/go`, `~/.npm`, the pnpm store): plan-0.8 headline 1, step 2.

- **The `php-app` template lets a recipe name an extension its PHP already has.** `xml` in `php-extensions` makes every PHP command print a module-already-loaded warning on stdout. nextcloud-nixgen's install check read it as the database type (2026-09); limesurvey-nix's install probe read it as "installed" and served a database with no schema (2026-09-29). Recipes now leave `xml` out and say why, and the probes refuse an answer that is neither yes nor no. By construction: the template could filter out what `enabled` already holds, so a recipe cannot name it twice.

- **invoice-ninja-nixgen's Composer dependencies failed to build once on a cold store, 2026-09-29, then built.** Inside the fixed-output derivation, Composer's download of `goetas-webservices/xsd2php-runtime` was "not a valid zip archive" (unzip error 35); the same derivation had built an hour before and built again on the retry. An upstream archive served truncated, most likely. Nothing retries it, and a cold-store run depends on every such download succeeding once.

- **uptime-kuma's sign-in probe failed once on Docker, 2026-09-28, then passed.** The deploy's own check signed in as `hop3probe`; in the same second the harness's check was refused ("Incorrect username or password for user hop3probe"), and its next socket.io connection got no first message within 8 s. Two credentials, or a race with `[probe].create`? A result that depends on timing is a platform bug until shown otherwise.

- **`.NET` on Fedora is untested.** An installed SDK now counts as available (`rpm -q`), in case `dnf list --available` leaves it out, as the 2026-10-06 review recalled; no Fedora run has confirmed either half.
- **`GitHubSource` carries placeholder fields** (`archive = "directory"`, `executable`) so templates that test `source.archive` take the right branch. Templates should branch on the source's kind; a recipe can no longer set the inert keys, so the fields are dead weight rather than a trap.
