### 1. An authenticated gate in front of apps

An app is public the moment it deploys. That is right for an application with its own accounts and wrong for the class people actually deploy: scripts with a web page, generated tools, admin dashboards, staging copies. The only access control today is `[waf]`, whose gate keys on named networks. `require = "auth"` is a hard validation error until forward-auth exists ([ADR 050](adrs/050-waf-l7-lewaf.md) §5).

Scoped on 2026-09-22 into two proposed ADRs and three pieces of work, in this order:

1. **Standard roles and control-plane authorization** ([ADR 061](adrs/061-standard-roles-and-rpc-authorization.md)). Prerequisite, **done**: an account created to pass a gate could otherwise run `env show` on every app. Four fixed roles (`admin > deployer > viewer > member`), one per account, enforced in the RPC dispatcher and the dashboard, default-deny; `hop3 user set-role`; new accounts are members and get no token. Per-app grants are designed in and not built. No custom roles.
2. **Caddy and Traefik green in e2e**, **done**: `c_e2e/test_proxies.py` runs one container per proxy and sends each the same requests (plain HTTP, the HTTPS redirect, HTTPS, a php-fpm app, a `[waf]` app). Caddy failed validation on every deploy and Traefik routed nothing on port 80; both are fixed, and a proxy now refuses before the build what it cannot serve (FastCGI and files on Traefik, the WAF on both, certbot on Traefik). The admin-domain route moves to the gate: the e2e image has none for nginx either, and the gate is what needs it on all three. Teaching the installer to install Caddy and Traefik is a separate item, and it needs certificates made proxy-aware first: certbot issuance writes a temporary nginx vhost and reloads nginx, and renewal (`platform/cert_renewal.py`) installs into `NGINX_ROOT` and calls `reload_nginx()`, so both are refused elsewhere (the `hosts_certbot` capability). The per-proxy half exists: each plugin writes `<root>/<app>.crt` and Caddy serves the challenge webroot. The installer must also give each proxy an admin-domain route (the e2e image's entrypoint does it for all three) and set Traefik's `aliasHeadersStrategy: delete` on its entry points, which the access gate relies on.
3. **The gate** ([ADR 062](adrs/062-authenticated-access-gate.md)), **done**: `[access] require = "auth"`, a minimum `role`, `public-paths`, on nginx, Caddy and Traefik, with the acceptance list as `c_e2e/test_gate.py` on each proxy. The one-time code is bound to the browser that started the sign-in (login CSRF, 2026-09-25). One open question stays in the ADR: bearer tokens for scripts.

**Acceptance bar** is ADR 062's eleven-point list, one e2e per proxy. It includes the case that motivates ADR 061: a `member` who passes the gate is refused by every mutating RPC command.

**Size:** L. It unblocks fourteen login-less applications identified in a migration study and three catalog candidates with no sign-in of their own (synapse-admin, Outline, Woodpecker), closes ADR 050's own deferral, and is the largest single unblock in the backlog. Displaced three weeks running.

## Dependency management

- **Pin runtime dependencies.** `hop3-server` (and the other workspace packages) still use loose floors like `litestar[standard]>=2.22.0`. Hop3 is an application. Applications pin their runtime deps to exact versions, with controlled bumps. This avoids two failure modes seen in production: (1) pip's `only-if-needed` upgrade strategy leaving stale transitive deps on the server (e.g. litestar 2.18 satisfying `>=2.18.0` while local code uses 2.22-only APIs), and (2) silent drift between developer machines and the production server.

  Likely shape: `requirements.lock`-style file generated by `uv pip compile` (or `uv lock` with `package = true` flipped), used by the installer's pip step and pinned at PR time.

  The seven-day cooldown (2026-09-23) bounds how new an unpinned dependency can be on a server. It is not a pin, and two installs a month apart still resolve differently.

  Scoped to 0.5 release prep originally and never done; carried as an open box in [`plans/plan-0.7.x.md`](plans/plan-0.7.x.md).

## CLI

- **Add `hop3 validate`.** A local, client-side lint of a project's `hop3.toml`: run the server's schema validation (`ContextSection`, the committed-credential tripwire, field/host-safety checks) on the file at/above the CWD and exit 0/non-zero with no server required, so it can gate CI. Top-level and project-rooted, the dry sibling of `hop3 deploy` (no `--app`; the app comes from `[metadata].id`). Renamed from the obsolete `hop3 config validate` idea, which clashed with the `config`→`env` alias (ADR 036 D17). Original intent: ADR 001 §Consequences, ADR 027 §Developer Experience. (ADR 027 also lists a stale `hop3 config show` / `config export` from the same wishlist. Revisit if those are still wanted.)

  A checker already exists. `hop3check`, shipped from the `letscode-plugins` repo, is the one the packaging skill tells people to run. It implements the same rules by hand. It reports clean on recipes the server then refuses at deploy time. Since the php-fpm migration it also reports `nothing-to-run` on every PHP recipe, which is now the correct shape for one. The drift runs both ways, so whichever side is right on a given rule, two hand-written implementations of one contract will keep disagreeing. Whatever ships here should validate against the published `schema/hop3.toml.schema.json`, so the file holds one implementation.

- **`--` does not survive flag parsing.** `parse_flags` consumes the POSIX end-of-options marker (`_END_OF_FLAGS` in `commands/flags.py`) and records nothing about where it was, so a later pass cannot tell an escaped flag from one of ours: `hop3 apps -- --help` still reads as a request for hop3's own help. The `run` boundary has the same shape and is handled (`app_scope.RunBoundary`, fed by both passes); `--` needs a change to what `parse_flags` returns, which is why it was not folded in with it.

- **`hop3 login --token <token>` puts a secret on argv**, where `ps` can read it for the length of the call. ADR 036 gives `user add`, `user set-password` and `auth get-token` the `KEY=-` / `KEY=@file` / hidden-prompt treatment; the `--token` path never got it. The deployer is a caller (`deployer/deploy.py`, whose own comment at the call notes there is no stdin form to use). Small, and the rewriting machinery already exists in `commands/arguments.py`.

The items below come out of the 2026-09-25 pass that lined the client's argument handling up with the server's (see "Two Parsers Read One argv" in [`lessons-learned/cli-ergonomics.md`](lessons-learned/cli-ergonomics.md)).

- **The `waf` commands take the app as a positional.** `waf logs [<app>]`, `waf bans list [<app>]` and `waf bans clear <app> [<ip>]` break ADR 036 D5 (the app is always `--app`), so `hop3 waf logs --app x` is refused by the client and a project's ambient app is never used. Move them to `--app`: an optional filter for `logs` and `bans list` (the `_EXPLICIT_ONLY` set in `hop3_cli/core/app_scope.py`), app-scoped for `bans clear`. Keep the positional working behind a deprecation for a release. Once they read `--app`, the guard in `test_app_scope_matches_server.py` checks them like every other command.

- **Delete the RPC `git-hook` command, or find its caller.** `commands/git.py` `GitHookCmd` duplicates `hop3-server git-hook` (`server/cli/git.py`), which is what the post-receive hook runs. The RPC version reads the server process's stdin, so over RPC it can only answer "No push data received". The guard test exempts it by name (`NOT_SENT_BY_THE_CLIENT`); the exemption goes with it.

- **Most client messages still wrap at 80 columns when piped.** Rich word-wraps at the console width, which is 80 when the output is not a terminal. `print_text`, `print_summary` and `print_error` pass `soft_wrap=True`; warnings, info, success, progress and log lines do not, so a script reading them gets hard newlines mid-sentence. One setting on both consoles (`Console(soft_wrap=True)`) would cover them all, once tables are checked to lay out the same.

- **`hop3 app logs` has no follow mode.** Nine tutorials reached for `--tail`, which it never had; they now show the last 100 lines. Following a running app's log (streamed, like `hop3 deploy`'s output) is what they wanted.

- **Decide whether a no-op addon command succeeds.** `hop3 addon destroy x --type redis` for an addon that does not exist answers "does not exist" as plain text and exits 0, and `hop3 addon detach` of an addon that is not attached does the same. That can be idempotence (`rm -f`) or a silent failure; whichever it is, the help should say so and the exit code follow.

- **`hop3 system status` exits 0 on warnings.** Its help said a warning exits non-zero; the client only fails on an error item, so the help now says "when any check fails". If a degraded server should fail a script's check, the server has to say so explicitly (a distinct item or exit code), not the help.

- **Check the scripting examples in `docs/src/guides/cli-migration.md`.** They pipe `hop3 backup list --app myapp --json` into `jq -r '.data[].id'`, but `--json` prints the list of response elements (here one `table`), not a `{"data": [...]}` object. Unverified against a server; the docs guard checks the command line, not what a pipe does with its output.

- **Some ADRs name commands that were never built.** The docs guard skips ADRs, because they record proposals: ADR 031 (`hop3 blueprints ...`), ADR 032 (`hop3 releases`, `hop3 rollback <app> [<version>]`), ADR 036 (`hop3 env set --from-file -`, `hop3 backup download <id>`). Where the design settled on other names (`app rollback --app`, `catalog install`), the ADR should describe it with those, so a reader does not take a dropped spelling for the CLI.

## Testing

- **`hop3-deploy-server --docker` never configures the local CLI.** Every Docker deploy in the upgrade chain, 0.7.5's included, logs "Could not configure the local CLI for http://localhost:8000 … Authentication failed: Authentication required" and carries on. The step (`deployer/deploy.py`, `_fetch_admin_token` then `hop3 login --token`) mints a token with `hop3-server admin:token` after an `admin:create` whose result it ignores (`check=False`); a token naming an account that was never created is refused since ADR 061's prerequisite. Not yet diagnosed past that reading. The harness is unaffected (it fetches its own token), but an operator's `hop3-docker` context is left unusable behind a warning.

- **A deploy whose uWSGI config is refused reports a timeout.** In the e2e image (whose uWSGI has no Python plugin) a `wsgi:` worker's vassal is refused at once, `[strict-mode] unknown config directive: virtualenv`, and the emperor curses and throttles it. The deploy waited its full 60 s, then said the app "did not respond to health checks" and suggested raising `start-timeout`. The emperor's own words were in its log the whole time; the readiness diagnosis should read them (the Lessons Checklist already says to detect crashes from the process manager's words).

- **Real apps behind the access gate run only on a server with an admin domain.** `180-flask-gated` needs one, and the runner leaves it out, with a warning, on a server without: the Docker target, and a remote server addressed by IP. The catalog runs address their box by IP and select by status, so neither picks it up. Where the gate should run regularly is undecided: target the box by its hostname and include the fixtures, or give the harness's Docker and IP targets an admin domain of their own.

- **The Docker e2e target lets two sessions share one container without either knowing.** The target has a fixed container name (`hop3-server-test`) and fixed ports, so a second `pytest packages/hop3-server/tests/c_e2e/` started while one is running tears the container down and re-installs it under the first. Neither session is told. The result is a corrupt failure: each run sees the other's server restarts, addons and database rows.

  Observed 2026-09-11 with two sessions live at once. Seen from inside, every symptom had the same cause. `RemoteDisconnected` / `Connection refused` meant the other session was restarting hop3-server. `Authentication required` (exit 4) and `The server redirected the RPC call to /rpc/` meant a server had restarted under a live client. An nginx reload reported "no fresh worker processes appeared within 15s" because hop3-rootd, which performs that verification, was itself restarted mid-verify. `test_list_and_filter_backups` failed because `hop3 backup list` returned **the other session's app** and none of its own.

  `notes/lessons-learned/deployment-diagnostics.md` already says one e2e session per machine and that a failure seen while another session was active is not evidence. The harness does not enforce it. **Fix shape:** the Docker target should detect that the container is already owned by a live session (a lock file carrying the owning PID, or a label written at start and checked before teardown) and abort with a message naming the owner. A session that steals a running container breaks the "no silent fallback" rule, here in the test harness itself.

- **`--clean` does not clean the named volumes, so a poisoned download cache survives a blank-slate rebuild.** mediawiki failed nine times with `tar: Unexpected EOF`, identically across runs that were supposed to share no state, because `hop3-download-cache` held a 45 MB entry for a 116 MB tarball dating from 2026-08-24. `--clean` replaces the container and leaves the volumes, which is usually what you want and is exactly wrong for a cache. A truncated entry there is indistinguishable from an upstream fault. It is also the one piece of state that makes a failure look reproducible when it is not. mediawiki passes on a remote target, which finally separated the two. **Fix shape:** validate a cache entry on read (size against the recorded `Content-Length`, or a checksum when the recipe gives one) and evict a short file; separately, say in `--clean`'s own output which state it is not clearing.

- **The e2e image build fails intermittently on apt.** `E: Sub-process /usr/bin/dpkg returned an error code (1)` while installing the 25-package catalogue baseline, and `.NET SDK 9 installation failed` alongside it; the run dies in fixture setup before any test. Not disk (host and Docker VM both had >17 GiB free). Seen 2026-09-11, under the same two-session conditions as above, so re-confirm on a quiet machine before chasing it.

- **`hop3-deploy-server --docker` cannot configure the local CLI, warns, and carries on.** Every Docker deploy prints `[5] Configuring local CLI`, then `⚠ Could not configure the local CLI for http://localhost:8000`, `⚠ Verifying connection…` and `⚠ Authentication failed: Authentication required.`, and the deploy reports success. The harness never notices, because it fetches its own token (`hop3-server admin:ssh-token`) and does not use the local CLI configuration. A developer running `hop3-deploy-server --docker` by hand gets a server the CLI cannot talk to, announced as three warnings. Seen 2026-09-24 in runs before and after the harness's token change. **Fix shape:** configure the CLI the way the harness authenticates (a token from `admin:ssh-token` inside the container), and abort when that fails.

## Packaging

- **A GitHub-generated tarball does not hash stably, and the Nix generator pins one anyway.** `Source.as_nix` always emits `pkgs.fetchurl`, so a recipe fetching `https://github.com/<owner>/<repo>/archive/refs/tags/<tag>.tar.gz` pins the bytes of an archive GitHub *generates on request*, and Nix says so during the build: `warning: archives from GitHub revisions should use fetchFromGitHub`. owncast-nixgen failed the 2026-09-12 catalog run exactly this way (`specified: sha256-ID9A…` / `got: sha256-nIsP…`) for a five-year-old tag that had not moved.

  **Three incidents in two weeks, three failure modes, one cause** (2026-09-22): owncast-nixgen's tag tarball was regenerated and its hash moved; mediawiki's download truncated; uptime-kuma's answered `504 Gateway Time-out` six times during the 0.7.5 gate. Every one of them is GitHub generating an archive on demand. Re-hashing repairs an instance. The class stays open: the same tag can move again tomorrow. `fetchFromGitHub` fetches via git and normalises, so its hash is stable. It hashes the *unpacked tree*, so switching the emitter invalidates every recorded hash for a GitHub source and needs a re-hash pass over the affected recipes. **Decision needed**: re-hash the one and carry on, or take the migration. The migration pairs with the nixpkgs pin bump, which wants a one-pass re-record of its own.

  **Taken, 2026-09-25, with the nixpkgs pin bump.** A nix-gen recipe names the repository instead of an archive (`[nix] github = "OWNER/REPO"`, `rev`, `hash` of the unpacked tree), and a GitHub `/archive/` URL is refused with the command that prints the hash. The ten affected recipes moved over, each hash proven by realising the fetch locally. The default pin moved from nixos-24.11 to nixos-26.05, with a test that fails once it is more than two releases behind; every nix-gen recipe evaluates on it (directus by moving the pnpm default to pnpm_10, forgejo to go_1_25). Redmine moved to 6.1.4 (SF: "Upgrade") in both its Nix recipes, which needed a platform capability: `ruby-bundler` could not build a gem with a Rust extension (commonmarker 2), and now takes `gem-cargo-hashes`, the recipe nixpkgs' own redmine package uses. gitea-nixgen builds Gitea 1.22.6, whose logger races at startup under every Go since 1.24 (`concurrent map read and map write`, every start; Go 1.25 did not help): it stays on its own nixos-24.11 pin and Go 1.23, where it was verified. The way off is a supported Gitea: nixos-26.05 packages 1.27, whose pnpm 11 frontend and `go.mod` rewrite go-source cannot express yet. The five hand-written `-nix` recipes that fetched a GitHub archive in their own `hop3.nix` (invoice-ninja, bookstack, dolibarr, kanboard, and cryptpad in `broken/`) were converted the same day.

  **Run 1 on hop3-dev, x86_64, every Nix recipe: 58 of 63 passed.** Every converted recipe that ran built, hand-written and generated. Two dependency hashes moved and were re-recorded from the build's `got:` (directus-nixgen `node-deps-hash`, radicale-nixgen `pip-deps-hash`); the others held. gitea-nixgen crashed at start (the logger race above). vikunja-nixgen failed on a path the conversion broke: `go-frontend-source-root` named the tarball's top-level directory, and it now names a directory in the repository, found with `setSourceRoot` whatever the fetch unpacks to. redmine-nixgen needed a server with `gem-cargo-hashes`, which run 1 predated; redmine-nix built Redmine 6.1.4 with commonmarker's Rust extension from vendored crates and served its sign-in page. Every recipe that needs a 0.8 server says so with `requires_hop3 = "0.8"` (fourteen nix-gen recipes). **Runs 2 to 4**, each with the server redeployed from the tree: 60 of 63 in run 2 (redmine-nixgen built Redmine 6.1.4 through the new `gem-cargo-hashes`), then gitea-nixgen on its own nixos-24.11 pin and vikunja-nixgen (pnpm_9 on its own pin, the pnpm hash re-recorded) green with their sign-in checks. **62 of 63.** The one left is directus-nixgen, alpha: the pin bump walked it through three template bugs, now fixed (a silenced pnpm install, an install from the read-only store, a native rebuild pnpm 10 skipped without a word), and then into `isolated-vm` 5.0.3, which does not compile under GCC 14 (blocker #38). The catalog side cannot be published before 0.8: a 0.7 server rejects `[nix].github` as an unknown key.

- **`NGINX_INCLUDE_FILE` and `CADDY_INCLUDE_FILE` resolve against the app directory, not the source tree.** Both plugins read `Path(self.app_path, <value>)`, so an include shipped in the app's repository is found only if the recipe writes `src/` in front of it, and a bare name gives `File not found: /home/hop3/apps/<app>/<name>` (seen 2026-09-25). Neither variable is documented. Decide which directory the value is relative to, say so where it is read, and test it.

  **Fixed, 2026-09-25.** The value is a path in the app's source tree, which is where a recipe ships the file; both proxies read it through one `BaseProxy.include_file`, which refuses a path that resolves outside the tree (a symlink included) and a missing file, each with a diagnosis naming the variable. Left undocumented on purpose: the typed `[proxy]` keys are the supported surface, and the include still runs through `expand_vars`, so a snippet copied from upstream can have its `$variables` rewritten (blocker #24).

- **A catalog entry cannot say which server it needs.** The published catalog is read by every deployed server, whatever its version. When a recipe uses a key an older server does not know (`[nix].github`, 2026-09-25), the only protection is not publishing it until every server has upgraded, which nothing enforces. A `requires-hop3 = ">=0.8"` in `catalog.toml`, checked by the server before it installs and shown in the listing, would let the catalog move ahead of the slowest server safely.

  **Done, 2026-09-25.** `requires_hop3 = "0.8"` (a plain release number, so no range syntax to get wrong) in the `[catalog]` overlay. `hop3 catalog install` refuses a recipe that needs a newer server by name, before it creates anything; the publish step refuses a malformed value, and now reads the overlay at all, which it did not before. A development build counts as its release. Servers older than 0.8 ignore the key, so the rule "publish only after 0.8 ships" still holds for this release. Not shown in `hop3 catalog list` yet: the refusal is what matters, and the listing's columns are a separate change.

- **A recipe can pin its Node version but not its package manager.** `[build].node-version` installs an exact Node into the app's venv; pnpm was whatever the host happened to have. Etherpad's `download.sh` carries three separate workarounds for successive pnpm behaviour changes (`auto-install-peers` moving out of `.npmrc`, dependency build scripts needing `dangerouslyAllowAllBuilds`, and `pnpm ls --no-production` being removed, which is fatal at *startup* because upstream's plugin migration calls it). Each was written blind against whatever pnpm was current that week.

  **The server-wide half is done (2026-09-14):** the installer pins an exact pnpm and reconciles it on every run, so the version stops moving under deployed apps and two servers of the same Hop3 version agree. Two questions remain. An app needing a pnpm other than the server's still has no way to ask for one (the *per-app* pin). The package-manager *selection* question (dispatch from the lockfile) is separate. Both scheduled as sub-items under [`plans/plan-0.8.md`](plans/plan-0.8.md) headline 4; neither is urgent now that the drift is stopped.

  **A third axis, found on 2026-09-21: the Nix path uses neither.** `node-pnpm-install` runs whatever pnpm the recipe's pinned nixpkgs carries (9.15.9 for the one recipe on that template), so the installer's server-wide pin does not reach it and `[build].node-version` says nothing about it. The versions differ in behaviour that matters: pnpm 9's `fetch` compiles native addons while populating the store, 11's does not. Whatever answers the per-app question has to answer it for the Nix builder too, or the two builders will keep resolving the same recipe differently.
