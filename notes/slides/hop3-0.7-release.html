▹ 03/Resilience · M3.204 / 13

Upgrade without holding your breath

Every app upgrade is a transaction: it snapshots first, verifies health after, and restores the snapshot itself if the build, a migration, or the health check fails.

hop3 · app upgrade
$ hop3 app upgrade --app myapp
✓ snapshot 20260707_120000_ab12cd created
✓ rebuilt · ran before-run migrations
✗ health check failed, rolling back…
✓ restored to 20260707_120000_ab12cd. App is up.
$ hop3 app rollback --app myapp --to 20260706_090000_9f3ac1
# a foreign backup id is refused (app-scoped only)
// the app

upgrade & rollback

upgrade is the safe redeploy a plain deploy lacks; rollback restores the most recent app backup on demand.

// the server

can't fake "complete"

The deployer confirms hop3-server actually answers before reporting success; otherwise it fails loud with the exact revert command.

// proven

upgrade-chain e2e

Install a baseline, then hop a version chain: green on Docker and a fresh Hetzner VPS, each version by its own installer.

▹ 04/Backing services · M3.105 / 13

Email is a swappable backing service

Symmetric with the database addon: the operator picks a backend once, an app opts in by attaching an email addon, and apps always talk to a loopback SMTP endpoint, never the provider directly. Swap the backend without re-touching a single app.

relay supported

Provider or smarthost

Point Hop3 at any transactional-email provider or corporate smarthost (bring your own). SASL+TLS to the submission port, DKIM auto-verify, and a deliverability pre-flight.

catch supported

Dev sink

Captures every message and never sends it. Validated end-to-end: the safe default for staging and demos.

direct preview

Your own MTA

Postfix delivers to recipients' MX and opendkim signs. Hop3 prints the SPF/DKIM/DMARC records to publish and never fakes "ready" over unpublished DNS.

$ hop3 server email backend relay --smtp-host smtp.your-provider.com --from-domain example.com   # → 127.0.0.1:25 null-client queues and forwards; apps only ever see SMTP_HOST=127.0.0.1
New in 0.7relay + catch validated end-to-end · direct in preview
▹ 05/Ethos · robustness06 / 13

Fail loud. Never lie.

The through-line of 0.7: a success message is a promise. When Hop3 can't keep it, the failure shows up where you look. A green checkmark never covers a broken box.

// health

A 200 alone isn't "healthy"

Content-aware checks (contains) mark a deploy healthy only when the app serves its own page. A placeholder or an error page fails the check.

// alerts

Broken things reach you

Opt in and get emailed on cert-renewal failures (before expiry) and failed deploys. Best-effort, and never masking the failure itself.

// proxy

No silent nginx reload

Admin-domain and TLS setup stop the deploy when nginx can't reload. A "complete" deploy never hides a domain nginx never picked up.

// ops

The right restart, every target

Restart and nginx reload pick the mechanism the target actually uses (systemd or supervisor), so a deploy can't silently keep serving old code.

Errors are never silentno fake success · no silent skip

▹ 07/Security · architecture08 / 13

Security by boundary and design

A narrow root boundary, a firewall roadmap, and a plugin core: the machinery that lets many real apps share one server without stepping on each other.

// rootd · ADR 041

Privileged-ops daemon

The operations that need root run through one small, audited daemon. The privilege boundary is a single narrow, reviewable seam (no broad sudoers).

// LeWAF · ADR 050

Pure-Python WAF landing

An OWASP-CRS engine: schema, SecLang compiler, engine plugin, and named networks are merged. The proxy-running slice lands in 0.8.

// ADR 045 / auth

Hardened and isolated

Fixed-port registry and network firewall; the June 2026 auth audit remediated; hop3.toml holds zero secrets.

// Pluggy + Dishka

Everything is a plugin

Builders, language toolchains, deployers, addons, proxies, and OS support: extend the platform without forking it.
