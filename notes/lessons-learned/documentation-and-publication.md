# Lessons Learned: Documentation, Reports and Publication

Hop3 publishes a lot: a documentation site, a blog, four technical reports, twenty experience reports, sixty ADRs and a public notes tree. That surface has its own failure modes.

## Know which tree is public before you write in it

`notes/` is tracked in git and pushed to GitHub **and** to an external GitLab. Its internal counterpart is gitignored. The two look identical in an editor, and nothing in the writing experience distinguishes them.

A planning document was drafted in `notes/plans/` that named an undecided funding application, its scope and milestone structure, plus the reasoning for holding work back. All of it was correct and none of it publishable. It was one commit away from two public remotes. It was caught only because someone asked whether the directory was public.

- **Check the destination's publication status before drafting.** `git check-ignore -v <path>` answers it in a second.
- **When a document has both a public and a private half, split it.** The public file states what is deferred; the private one states why. A single file trying to do both ends up either indiscreet or uselessly vague.
- **Give the private file a header that says it is private and where its public counterpart lives.** Someone will eventually try to "tidy" it into the public tree.

## Documentation is a claim, and claims rot silently

Three of the entries turned up in one week:

- `CHANGES.md` announced that a test now scanned every package for credentials in argv. No such test existed. The intent was real; the sentence shipped ahead of the code.
- A technical report described figures as "regenerated by a published script" when the script did not exist and the protocol postdated the results.
- The privacy policy named Matomo as the site's analytics platform while the site was being fitted with Umami.

The rule that came out of it is to describe only what actually happened and to prefer a checkable claim over a flattering one. "Preliminary, single-sample" is a fine thing to publish; "regenerable by a published script" is not, unless the script is in the repository. Where a claim can be mechanised, mechanise it: `hop3-tools catalog reports` validates every experience report's header against the recipes and against git history, so a report that goes stale fails a check.

A corollary follows: when you change a mechanism, grep for the documents that describe it. Deploying a new analytics tracker made the privacy policy false the moment it shipped; the fix belonged in the same change.

## An advertised number needs a gate

The project advertises twenty curated catalog applications, in the report, the blog, the README and the dashboard. The published catalog index carried fifty-five entries: each application's `-nix` and `-nixgen` packaging variants shipped as separate installable entries, so an operator browsing saw BookStack three times.

Nothing was wrong with any single component. The variants are legitimate, the loader is correct, the count is correct for what it counts. The number we advertise was never checked against the artefact we publish. Any figure repeated across several documents should have exactly one gate that fails when it drifts. The gate belongs at the point of publication.

## Edit the source tree, not the generated one

Two traps cost time:

- `docs/blog/posts/` is the source; `docs/src/blog/posts/` is generated from it by `preprocess_markdown.py`. An edit to the generated copy lasts only until the next build.
- The tutorials work the same way: source in `docs/tutorials/`, generated into `docs/src/tutorials/`.

The same mistake has a publication-order variant: a run with `--recipes published` installs from the **published** catalog, so editing `apps/` and re-running silently re-tests the old recipe. Publishing is part of the edit-test loop.

## When output looks wrong, suspect the renderer before rewriting the source

The report PDF rendered two architecture diagrams as tangles, with nodes scattered, edges routed around the page, a figure split across a page break. The obvious reading was that the diagrams were badly written, and rewriting them was the obvious response.

They were fine. The report's build pipeline was converting Markdown with `md2typst`, whose *default* mermaid backend is a pure-Typst renderer. It ignores direction hints and mangles rank assignment. Rendering the identical source with `mmdc` (the reference renderer) produced correct output immediately.

**Reproduce the artefact through the same pipeline that produced the bad one, then change one variable.** In this case: extract the diagram source, render it standalone, compare. If the standalone render is correct, the fault is downstream of the source and no amount of rewriting will fix it. (The eventual fix was to pre-render the figures with `mmdc --pdfFit` and hand the pipeline an image.)

A related trap in the same pipeline: a theme override that extends the base template alone is served **without** whatever the main template adds. Blog posts silently lost the analytics tag that way: visible only by counting pages in the built output.

## An error must name its input

A documentation build failed with a YAML scanner traceback ending in `mapping values are not allowed here`, quoting the offending line but not the file. Thirty blog posts were in the build. One of them had an unquoted `description:` containing a colon.

The parser had the path; two of its call sites wrapped the exception to add the filename and one did not. The one that did not was the one that ran first. The fix belongs in the function that raises, which also removes the duplicated wrapper. While there, the message gained the remedy:

```
docs/blog/posts/2026-06-testing-testlab.md: malformed YAML frontmatter: mapping values are not allowed here
  in "<unicode string>", line 6, column 34: …
A value containing ': ' must be quoted, e.g. description: "The Test Lab: making it legible".
```

This is the "fail-loud doctrine" extended by one clause: an error that does not identify *which input* it rejected has failed loud at the wrong thing.

## Report writing: what a review pass actually finds

Three review passes over one 20,000-word report, each finding a different class, in this order:

1. **Accuracy and consistency.** Duplicate table numbers, a claim contradicted by its own table (a figure quoted as "within 15%" that the table showed at 18%), a "three things" list containing four, cross-references to renumbered sections, counts taken from different snapshots.
2. **Style.** Measured: "rather than" appeared 94 times in 20,000 words, roughly once a paragraph. A device that is good once becomes a mannerism. The same applied to closing every paragraph on an aphorism.
3. **Tone before publication.** Passages that volunteer weakness the argument does not need: a shipped guard that had never executed, narrated in full; the two most damaging examples in the abstract; a version-maturity label that contradicted a milestone claim elsewhere in the same document.

**State the limitation.** One sentence that a mechanism was verified by fault injection and fixed carries the same information as a paragraph reconstructing how it was missed.

Two mechanical habits paid off: fix cross-references and numbering *last*, because earlier passes move things; and recompute every number from its source, which is how the corpus counts and the deploy-time medians were caught disagreeing with the tables they were drawn from.

## Executable tutorials are tests, with a test's discipline

The tutorials run on every fresh server, so their failure modes are test failures:

- **A virtualenv must never ship.** `venv/` holds symlinks to the local interpreter; archived and sent to the server they are dead links (`'venv/bin/python3.12' is a link to an absolute path`). The CLI filters the deploy archive by `.gitignore`. The tutorial's `.gitignore` excludes `venv/`, so the server recreates it.
- **A background server needs a bound life.** `python app.py &` in a tutorial hangs the runner forever; `timeout 5 python app.py &` ends when the check has run.
- **Fences come in pairs.** An unclosed ` ```output ` block swallows the next section and the parser fails well past the cause; verify fence pairs after any bulk edit.
- **Scaffolders prompt.** `npx create-next-app` asks about TypeScript and waits on a stdin that CI does not have; every scaffold takes `--yes` or runs under `CI=true`.
- **Verify a plain endpoint.** A health endpoint returning nested JSON invites a check that matches the wrong field; a `/up` that answers `OK` is verified by equality. Keep `/health` for humans.
- **The server provides runtimes; the tutorial installs its framework.** "rails not found" on a fresh server is correct behaviour: Ruby is the platform's, `gem install rails` is the tutorial's, which is how a real developer's server looks.

## A proposal's alternatives are undecided until someone decides

A plan listing alternatives to its proposals filed them as "considered and not adopted" on the author's behalf. The author had not decided; the document had. The maintainer's correction: they are "undecided potential alternatives", each with what it buys, what it costs and what evidence or event would settle it. A document that holds an unmade decision misleads the next reader and closes an open question; reserve "not adopted" for choices made in the conversation or in an ADR.
